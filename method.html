The Method

Security writing is full of commands nobody ran. GHOSTLIGHT files are held to a research standard instead: if a command appears in a file, it was executed on the named OS and version, and the output shown is what actually came back. When reality disagreed with the plan, the file says so. That is the whole method.

01

Named environment, always

Every file names the exact OS and version the walkthrough was verified on, down to the shell. If your versions differ and a step behaves differently, that is useful data, not your failure.

02

Transcripts are verbatim

Session transcripts are the literal commands and outputs from verification runs. Prompts are normalized to a clean user@lab form and pty noise is trimmed, but no command and no output is invented. The replay widget types the real thing.

03

Failures are published

When a defense does not work somewhere, the file names where and why. Example from GH-001: kernel audit watches cannot run in most containers, and append-only file flags do not exist on btrfs. Workarounds are given for each.

04

Attack first, defense last

Every file opens with the stealth working, so you respect the technique, and closes with detection, mitigation, and prevention, so you keep the fix. Green means verified safe. Red means hostile. Those colors never decorate.

05

Bypasses are named

Every countermeasure lists how it can be bypassed and what covers the bypass. A defense whose limits are hidden is a trap; a defense whose limits are stated is a layer.

06

Victim first

Each file answers two questions in order: how do I know whether this exact technique was used against me, and what exactly do I do about it. Theory serves those answers, never the reverse.

07

One way, not the way

Every tactic has many implementations and many resolutions. Each file demonstrates one observed way to achieve the tactic and one way to resolve it: a single worked instance, one step in the reader's longer journey of securing systems, never the definitive treatment.

08

Defenses are lab-built, framework-checked

Every defense is designed and verified in the lab first. MITRE ATT&CK and MITRE D3FEND are then consulted as candidate sources: when a framework names a defensive technique the lab already uses, the file cites it; when it adds genuine coverage the lab missed, the file adopts it. Frameworks never outrank a verified result, and a mapping is never forced where it adds nothing.

Environment notes Each walkthrough names its exact verification environment, including where that environment falls short. Most steps run on the named OS in a lab environment; any step that needs the kernel's audit subsystem is marked full VM only, documented from official sources rather than presented as lab-verified. The walkthrough tells you the exact check that distinguishes the two environments, and what we verified in each.

Safety Attack steps run against a dedicated test account on an isolated machine or VM. Nothing here is meant for production systems, other people's machines, or anything you do not own. The techniques are public MITRE ATT&CK entries; the value of this site is the verified defense, not the attack.

Corrections Reproduce a file and get a different result on the named OS and version? That is a bug in the file, and it gets fixed with credit. The standard only works if it is enforced.
