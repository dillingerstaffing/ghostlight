01

Intel Brief

CONTEXT

MITRE ATT&CK T1036.007: adversaries deceive by giving a hostile file a double extension, so the name claims one type while the bytes are another. This file names a benign shell script quarterly-report.pdf.sh, watches a directory listing read it as a document, watches file(1) read the bytes and say script, and runs the script to prove the kernel executes the bytes, not the name. Then the defense: ask the bytes, hunt the name/bytes mismatch across the tree with one command, capture evidence before stripping the execute bit, and install the scheduled sweep that flags the next plant. Two actors: the attacker, who owns the deceptive name and the execution; and the defender, who owns the file reads, the mismatch hunt, the evidence-first mitigation, and the sweep in the blue phase.

Why this technique. People read names left to right and stop at the first familiar extension. The kernel does not read names at all: it resolves execution from the file's bytes, starting with the shebang line. A name that claims PDF on a file whose bytes say shell script deceives exactly the reader who never checks the bytes, which is most readers, most of the time. The hiding place is not a tool bug; it is the gap between human reading order and kernel execution order.

Why not the honest name. The obvious alternative is notes.sh: same 37 bytes, one truthful extension. Break it on the concrete input: file says POSIX shell script, cat shows the script body, the name says script. Name, bytes, and content all agree, so there is no divergence for a deception to live in. The recording shows the measurement: the honest name leaves anyone reading the listing fully informed before anything runs. The double extension fixes exactly that failure: it makes the name disagree with the bytes, and the disagreement is what the eye skips.

The mechanism, in one line. A file extension is the suffix after the last dot, a naming convention, not a property of the file: nothing in the bytes changes when the name changes. Magic bytes are the file's first bytes, which file(1) reads to identify the real type. The shebang is the #! first line, which tells the kernel which interpreter runs the file. The double extension exploits the reader, not the kernel: the eye lands on "quarterly-report.pdf" and stops, while the kernel reads #!/bin/sh and executes. Terms earned, no borrowing.

The concrete case, before the abstraction. In /tmp/gh022: quarterly-report.pdf.sh, 37 bytes. ls -1 prints two names, and the attacker's name reads as a PDF report. file quarterly-report.pdf.sh: POSIX shell script, ASCII text executable. ./quarterly-report.pdf.sh prints GHOSTLIGHT-CANARY-022. Named as a document, ran as code. That gap, between what the name claims and what the bytes are, is the whole technique.

Scope. T1036 covers masquerading broadly: matching legitimate names or locations, right-to-left override, fake icons, double extensions, faked magic bytes. This file works the double-extension case end to end: the plant, the listing deception, the bytes check, the mismatch hunt, the evidence-first mitigation, and the scheduled sweep. The canary is a benign token: it proves execution and touches nothing else. The lab runs in a disposable namespace under /tmp because the blue phase plants, strips, and sweeps for real.

Build the lab

04

Phase Blue: ask the bytes

DEFENSE

The defender does not trust the name. The defender reads the bytes, hunts the mismatch across the tree, captures evidence before closing the execution path, and installs the sweep that flags the next plant.

Here is the trap: reading the listing, seeing a PDF report, and moving on. That is trusting the name the attacker chose. The detection starts by asking the bytes, which the attacker did not choose.

1

DETECTION: the naive view

cd /tmp/gh022 && ls -l: a clean lab, two 37-byte scripts, nothing hidden. Stopping here is the attacker's win: the listing was never checking the bytes, so a clean listing proves nothing.

bash
$ cd /tmp/gh022 && ls -l
total 8
-rwxrwx--- 1 root root 37 Sep 25 12:34 notes.sh
-rwxrwx--- 1 root root 37 Sep 25 12:34 quarterly-report.pdf.sh
2

DETECTION: ask the bytes

file quarterly-report.pdf.sh reveals the shell script behind the PDF name. The name is a claim; the bytes are evidence. No prior knowledge of the trick is needed: file reads the bytes, not the name.

bash
$ file quarterly-report.pdf.sh
quarterly-report.pdf.sh: POSIX shell script, ASCII text executable
3

DETECTION: the mismatch hunt, the runbook one-liner

ls -1 | grep -E '\..*\.' flags every name carrying two or more dots and passes over notes.sh, the single-dot control. One command, the whole directory. The tell, concrete: good is a name with one truthful extension; bad is a name whose extensions disagree with the bytes.

bash
$ ls -1 | grep -E '\..*\.'
quarterly-report.pdf.sh
4

DETECTION: the audit question

command -v auditctl answers /usr/sbin/auditctl: the audit tools are present in this lab. The rule for a real host is stated with its dependency, not demonstrated: auditctl -a always,exit -F arch=b64 -S execve -k execs records what actually executed regardless of the name, but it needs the audit subsystem enabled and its rules loaded. Where it runs, the good-versus-bad is concrete: good is an execve of a known deployment path; bad is an execve whose path contradicts the name the user saw.

bash
$ command -v auditctl || echo 'no auditd in this lab'
/usr/sbin/auditctl
5

MITIGATION: evidence first, then strip

mkdir -p evidence && sha256sum quarterly-report.pdf.sh | tee evidence/hash.txt && cp quarterly-report.pdf.sh evidence/ captures the hash and the file BEFORE the strip, because closing the execution path comes next. chmod -x quarterly-report.pdf.sh strips the execute bit. Verify: ./quarterly-report.pdf.sh fails with Permission denied, rc 126, recorded honestly. The execution path is closed; the evidence is preserved. Scope: the mismatch hunt covered the directory.

bash
$ mkdir -p evidence && sha256sum quarterly-report.pdf.sh | tee evidence/hash.txt && cp quarterly-report.pdf.sh evidence/
chmod -x quarterly-report.pdf.sh
./quarterly-report.pdf.sh
eb4f11ff28e29dd873ab052d324811c77d44c625e0bb03302c31f4b213482a30  quarterly-report.pdf.sh
bash: ./quarterly-report.pdf.sh: Permission denied
6

PREVENTION: the scheduled sweep

The heredoc writes sweep.sh: ls -1 "${1:-.}" lists the target directory, defaulting to the current one, and grep -E '\..*\.' keeps only the names carrying two or more dots. chmod +x; ./sweep.sh . flags quarterly-report.pdf.sh. Honest note, shown live: the attacker's file lost its +x but keeps its name, so it still flags. The name is still deceptive; the execution is closed. The sweep watches names, not permissions.

bash
$ cat > sweep.sh <<'EOF'
#!/bin/sh
# mismatch-sweep: flag names carrying two or more extensions.
# Run on arrival and download trees; any hit gets file(1) before it gets executed.
ls -1 "${1:-.}" | grep -E '\..*\.'
EOF
chmod +x sweep.sh
./sweep.sh .
quarterly-report.pdf.sh
7

PREVENTION: the next plant, demonstrated live

printf plants a NEW arrival, invoice.pdf.sh, and chmod +x arms it. ./sweep.sh . flags both deceptive names. The next plant is caught by the sweep, demonstrated live against this lab. Honest limit: this catches the naive double extension, not T1036.008 (faked magic bytes) or a single-extension lie; the poll interval sets the detection floor.

bash
$ printf '#!/bin/sh\necho GHOSTLIGHT-CANARY-022\n' > invoice.pdf.sh && chmod +x invoice.pdf.sh
./sweep.sh .
invoice.pdf.sh
quarterly-report.pdf.sh

05

Countermeasures

DEFENSE

Three moves, in order: close execution with evidence first, sweep on a schedule, enforce an execution policy. Each is one way, not the way.

1

Mitigate: capture, strip, re-sweep

Proven first against the live plant: sha256sum | tee and cp capture the hash and the file into evidence/ BEFORE the strip; chmod -x closes the execution path; the failed re-execution (Permission denied, rc 126) and the mismatch hunt confirm scope. A real response then hunts the delivery vector: how the file arrived is the incident's open question.

bash
$ mkdir -p evidence && sha256sum quarterly-report.pdf.sh | tee evidence/hash.txt && cp quarterly-report.pdf.sh evidence/
chmod -x quarterly-report.pdf.sh
./quarterly-report.pdf.sh
eb4f11ff28e29dd873ab052d324811c77d44c625e0bb03302c31f4b213482a30  quarterly-report.pdf.sh
bash: ./quarterly-report.pdf.sh: Permission denied

Honest limit. Closing execution is not the same as understanding arrival: a second copy elsewhere with +x still runs, which is why the hunt covers the whole tree. chmod -x needs write permission on the file. The lab removes the tree for cleanliness; a real incident preserves evidence/ and the original file for forensics instead.

2

Monitor: sweep the tree on a schedule

The scheduled form of the phase-blue read: sweep.sh runs the one-liner over arrival and download trees, and the tell is any name carrying two or more extensions with an executable last one. Plus the execve auditd rule, stated with its dependency: it needs the audit subsystem enabled and its rules loaded, which this lab has (auditctl is present) but many containers lack. D3FEND D3-FMBV: File Magic Byte Verification is the production form of "ask the bytes".

bash
$ ls -1 "${1:-.}" | grep -E '\..*\.'
quarterly-report.pdf.sh

Honest limit. The sweep catches the naive double extension only; magic bytes can be faked too (T1036.008 Masquerade File Type), and a single-extension lie needs the file check, not the name check. The poll interval sets the detection floor: a file that lands and is removed between sweeps leaves no name behind, only the audit log, if auditd was watching.

3

Prevent: the execution policy

The demonstrated sweep detects; only an execution policy prevents. D3FEND D3-EAL: Executable Allowlisting is the durable control; in its production form it needs fleet control. Mail and gateway stripping of double extensions is the chokepoint form, stated with its dependency on the mail and gateway stack. Honest note, repeated because it matters: the sweep detects; only the execution policy prevents.

Honest limit. Allowlisting is the strongest control here and the heaviest to operate: every legitimate script needs a rule, and the rule set needs ownership. Gateway stripping only covers the mail and download paths it sits on; a file arriving by USB or a shared drive never passes the chokepoint.

Countermeasures verified

The payload was hashed and copied before the strip, the strip closed execution (Permission denied on re-run), the scheduled sweep names its tell and flagged a newly planted arrival live, and the prevention control is stated with its dependency. Every control names its bypass: the sweep sees names, not bytes; the poll interval sets the floor; allowlisting needs fleet control; and only an execution policy prevents.

06

Debrief

TAKEAWAY

The name is a claim the eye reads left to right; the bytes are evidence the kernel executes. Ask the bytes before you run the name.

IOC checklist: signs this technique was used

  • A file whose name carries two or more extensions, especially with an executable last one
  • file(1) output contradicting the name's implied type (script bytes under a document name)
  • execve audit lines whose path contradicts the name the user saw (the auditd execs key)
  • New arrivals in download or mail trees with double extensions
  • No name/bytes mismatch check in the existing playbooks: the absence of the question is itself the gap

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, x86-64, on 2026-09-25
  • Both recordings are real executions on that platform, not simulations
  • Runs as root in a disposable namespace (the lab plants its own files; the assumed breach: something on the box wrote the deceptive name)
  • Cleanup: rm -rf /tmp/gh022; verify with ls /tmp
