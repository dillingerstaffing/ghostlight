01

Intel Brief

CONTEXT

MITRE ATT&CK T1622: adversaries check whether a debugger or tracer is watching them, and change behavior when one is. This file builds a four-layer stack around that check, then takes the defender's side with a different observer per layer.

Why this technique. A tracer is how an analyst watches a program run: strace logs the system calls a program makes. A payload that can tell it is being watched can choose to misbehave only when nobody is looking: exit quietly, decrypt nothing, sleep through the analysis. The check used here asks the kernel directly. Every process on Linux has a status file at /proc/self/status, and one of its fields, TracerPid, names the process tracing it, or 0 when none is. Reading that field costs one file read and no privilege, and it tells the payload exactly what the analyst hopes it cannot know: whether anyone is watching.

Why not a single layer. The obvious alternative is any one trick by itself. Break each on a concrete input. The tracer gate alone still leaves a visible file in a listed directory and a process running under its real name; an analyst who never attaches a tracer walks past the gate entirely. The hidden directory alone still shows the payload's real name in the process table. The borrowed name alone still sits in a directory that plain ls lists. Each layer defeats exactly one observer and leaves the others a clear view. That is why the stack exists: stealth is not one good trick, it is a set of tricks that cover each other's blind spots, and the price is that every new layer is a new surface a different observer can see.

The mechanism, with terms earned. A tracer attaches with the ptrace system call, and the kernel records the tracer's process id in the tracee's TracerPid field; strace is the tracer used in this file. /proc/self is the current process's own /proc entry, so /proc/self/status is the payload reading its own record, and the read must happen in the payload itself: a child process would report the child's own TracerPid, not the payload's, which is why the script reads the file with a shell loop instead of delegating to awk or grep. argv[0] is the process's self-reported name, set by whatever launched it; exec -a overrides it. The kernel keeps two facts that do not consult that story: /proc/PID/cmdline, the full command line including the real script path, and /proc/PID/exe, a link to the actual executable file. A dot-directory is a name beginning with a period, hidden from plain ls by a display convention from the 1970s, not by any filesystem enforcement.

The concrete case, before the abstraction. /tmp/gh010 holds one visible file, notes.txt, and one hidden directory, .sys-cache, holding sync.sh. Launched under strace, the payload reads a nonzero TracerPid and exits before touching its marker file. Launched clean with exec -a, it runs as syslog-helper, touches .marker, and sleeps. Plain ls prints one name. pgrep prints a boring one. /proc prints the truth.

Scope. T1622 Debugger Evasion covers every way a program detects analysis: TracerPid checks, timing checks, breakpoint scans. This file works the TracerPid case end to end on Linux, then stacks it with T1564.001 (the hidden directory) and T1036 (the borrowed name) to show how layers compose: each new layer defeats one observer and exposes a new surface.

02

Target Environment

LOADOUT

Ubuntu 24.04.5 LTS, bash 5.2, x86-64, strace. No privilege needed, no network, no persistence: the payload reads its own TracerPid, touches one marker file inside its own directory, and sleeps. The lab is one directory, one decoy, one hidden directory, one script.

1

Build the lab

One directory, one decoy file, one hidden directory. The decoy, notes.txt, is the boring visible file the casual listing sees.

bash
$ rm -rf /tmp/gh010; mkdir -p /tmp/gh010/.sys-cache && cd /tmp/gh010 && touch notes.txt && ls
notes.txt

A fresh lab directory with the decoy inside, and the shell moved into it. Now the payload, written into the hidden directory.

bash
$ cat > .sys-cache/sync.sh <<'EOF'
> #!/bin/sh
> # GH-010 lab: benign four-layer stealth stack stand-in.
> # Layer 1 (T1622): the payload itself reads TracerPid from
> # /proc/self/status and exits silently if a tracer is attached.
> # Then: touch one marker file inside its own directory, sleep.
> # No network, no persistence, no privilege.
> tpid=0
> while read -r key val _; do
>   if [ "$key" = "TracerPid:" ]; then tpid=$val; break; fi
> done < /proc/self/status
> if [ "$tpid" != "0" ]; then
>   exit 0
> fi
> cd "$(dirname "$0")" || exit 1
> touch .marker
> sleep 900
> EOF

The heredoc writes the payload exactly as written: the quoted 'EOF' keeps the shell from expanding anything inside.

2

The payload: sync.sh

Sixteen lines. Every line glossed, because the tracer gate lives or dies in this file.

sh: /tmp/gh010/.sys-cache/sync.sh
#!/bin/sh
# GH-010 lab: benign four-layer stealth stack stand-in.
# Layer 1 (T1622): the payload itself reads TracerPid from
# /proc/self/status and exits silently if a tracer is attached.
# Then: touch one marker file inside its own directory, sleep.
# No network, no persistence, no privilege.
tpid=0
while read -r key val _; do
  if [ "$key" = "TracerPid:" ]; then tpid=$val; break; fi
done < /proc/self/status
if [ "$tpid" != "0" ]; then
  exit 0
fi
cd "$(dirname "$0")" || exit 1
touch .marker
sleep 900

Line by line. #!/bin/sh runs the file under the system shell. The comment lines document the file; they do nothing. tpid=0 assumes unwatched until proven otherwise. The while loop reads /proc/self/status line by line in the shell itself: the redirection is opened by this shell, so /proc/self is the payload, and read splits each line into a key and a value with no child process involved. That detail is load-bearing: delegating the read to awk or grep would read the child's own status, not the payload's. When the key TracerPid: appears, its value is saved and the loop stops. If the value is not 0, a tracer is attached, and exit 0 dies silently: no error message, because an error message would itself be evidence. cd "$(dirname "$0")" moves into the script's own directory, so the marker lands beside the payload no matter where it was launched from. touch .marker is the only filesystem write the script ever makes, and the proof it executed. sleep 900 keeps the process alive for fifteen minutes, 900 seconds, so the defender has something to find. No network call, no cron entry, no startup script.

03

Phase Red: four layers on

ATTACK

Four layers go on, one at a time, each tested against the observer it is meant to fool. Every command below is copy-pasteable.

1

The interrogation

First layer on. The payload goes under the tracer.

bash
$ chmod +x .sys-cache/sync.sh && strace -f -o /dev/null ./.sys-cache/sync.sh; echo "rc=$?"
rc=0

rc=0. That is the exit code of a program that chose to die quietly, not of a crash: strace attached, the payload read a nonzero TracerPid, and it exited before its first write. -o /dev/null discards the trace itself.

bash
$ test ! -e .sys-cache/.marker && echo "no marker: tracer gate held, payload never ran"
no marker: tracer gate held, payload never ran

No marker. The gate held before any filesystem write happened. This is the file's end-to-end T1622 case: the check, the silent exit, the absent evidence. It is also the first signal the defender gets, and the blue phase spends it.

2

The clean launch and the borrowed name

Same payload, no tracer, and layer three goes on at launch.

bash
$ exec -a syslog-helper bash ./.sys-cache/sync.sh &
[1] 7415

exec -a sets argv[0], the process's self-reported name, before launching. bash is a real binary, so the borrowed name survives: had the payload been launched as a shebang script, the kernel would have re-executed the interpreter and dropped the borrowed argv[0]. The [1] line is the shell confirming the background job and its process id.

bash
$ sleep 1; test -e .sys-cache/.marker && echo "marker present: clean launch ran the payload"
marker present: clean launch ran the payload

Marker present. With no tracer attached, TracerPid reads 0, the gate passes, and the payload touches its marker and sleeps. Layers one and three are now both live: the gate that kills it under observation, and the name it wears when unwatched.

3

The drawer

Layer two was already in place: the payload lives in .sys-cache. Two commands, same directory.

bash
$ ls
notes.txt

One name: the decoy.

bash
$ ls -a
.  ..  .sys-cache  notes.txt

Four names. Nothing changed between the commands except the question. The -a flag tells ls to skip its dotfile courtesy.

4

The false name in the process table

All four layers live. Ask the process table who is running.

bash
$ pgrep -af syslog-helper
7415 syslog-helper ./.sys-cache/sync.sh

One process, wearing a boring name. pgrep matched the borrowed argv[0] against the pattern; the kernel's process table has no opinion about whether the name is true.

Stealth confirmed

Under a tracer the payload dies before writing a byte; unwatched, it runs from a hidden directory under a borrowed name while the default listing shows one decoy file. The hiding cost one leading dot, one borrowed name, one /proc read.

04

Phase Blue: change the observer

DEFENSE

The red phase trusted one observer per layer. Now change the observer for each layer, and watch every layer fall to a different one. Every command below is copy-pasteable.

Here is the trap: looking harder through the same observer. Staring at the process list for a suspicious name cannot beat a borrowed name, because the borrowed name was designed for exactly that stare. The fix is not a harder look. It is a different observer.

1

The listing still lies

Triage that stops at the default listing closes the case here.

bash
$ cd /tmp/gh010 && ls
notes.txt

One boring text file. Case closed, and the payload keeps sleeping.

2

argv[0] lies; the kernel does not

The process table never honored the borrowed name. It only repeated it.

bash
$ pgrep -af syslog-helper
7215 syslog-helper ./.sys-cache/sync.sh

Same sleeper, same borrowed command line. Now ask the two facts argv[0] cannot change.

bash
$ P=$(pgrep -f '[s]yslog-helper'); echo "pid=$P"; tr '\0' ' ' < /proc/$P/cmdline; echo; readlink /proc/$P/exe
pid=7215
syslog-helper ./.sys-cache/sync.sh
/usr/bin/bash

Three lines. The pid. The full command line: the borrowed argv[0] first, then the real script path it was launched with. And /proc/PID/exe, a link to the actual executable, /usr/bin/bash, which no argv[0] can rewrite. Two kernel facts against one self-reported name: that is what changing the observer buys.

3

Walk past the dot convention

find does not know about the dotfile courtesy. It walks the tree and matches names at the filesystem level, where a leading dot is just another character. -name '.*' matches every name starting with a dot; the quotes keep the shell from expanding the pattern before find sees it; sort orders the output.

bash
$ find /tmp/gh010 -name '.*' | sort
/tmp/gh010/.sys-cache
/tmp/gh010/.sys-cache/.marker

Two hidden paths, by their real names, marker included. The marker is the proof the payload executed here.

4

Kill the sleeper

Stop the process by the same kernel match pgrep used.

bash
$ pkill -f '[s]yslog-helper'; sleep 0.5; pgrep -af syslog-helper || echo "process gone"
process gone

pkill signals by name pattern. The [s] bracket keeps pkill from matching its own command line and killing the shell that runs it. The echo is the confirmation: no matching processes remain.

5

The gate confesses

The tracer gate was the payload's defense. Turned around, it is evidence. A process that dies the moment strace attaches is telling you it checks for tracers, and that confession costs the defender nothing: no payload execution, no marker, no risk.

bash
$ rm -f /tmp/gh010/.sys-cache/.marker && strace -f -o /dev/null /tmp/gh010/.sys-cache/sync.sh; echo "rc=$?"; test ! -e /tmp/gh010/.sys-cache/.marker && echo "no marker: gate held under tracer"
rc=0
no marker: gate held under tracer

rc=0 and no marker, exactly like the red phase. The defender learns the payload is tracer-aware without ever letting it run. This is the blue side of T1622: the check is itself a signal.

6

Remove the lab

Files last.

bash
$ rm -rf /tmp/gh010; ls /tmp/gh010 2>/dev/null || echo "lab directory gone"
lab directory gone

rm -rf removes the whole tree, hidden names included, because rm never asked the display either. The ls error is the confirmation: no such file or directory. No process, no files, no marker. Nothing persists.

Detection verified

Each layer fell to a different observer, the tracer gate confessed without the payload ever running, and the lab directory is gone.

05

Countermeasures

DEFENSE

Three moves, in order: change the observer, watch the writes, decide what may run. Each is one way, not the way.

1

Mitigate: compare observers, do not browse

In triage, stop asking any single tool and start cross-examining them. Compare the process table against the filesystem: anything executing from a dot-directory earns a closer look. Compare cmdline against exe: a borrowed name on a mismatched binary earns a closer look. This is the fleet form of the blue phase: the idea does not change, only the coverage. It clears the first-principles gate because it rests on what each tool actually promises: argv[0] is self-reported, exe is not.

bash
$ P=$(pgrep -f '[s]yslog-helper'); echo "pid=$P"; tr '\0' ' ' < /proc/$P/cmdline; echo; readlink /proc/$P/exe
pid=7215
syslog-helper ./.sys-cache/sync.sh
/usr/bin/bash
2

Monitor: watch writes, not names

A hidden file is still a created file, and a borrowed name still belongs to a real exec. File integrity monitoring (D3-FIM) notices the marker appearing in a watched directory regardless of its first character; the display convention is invisible at the layer FIM watches. Software inventory (D3-SWI) flags binaries that were never supposed to be on the machine, whatever their names start with. An EDR that logs process creation sees the real image path at exec time, before any argv[0] theater. Production versions run in the EDR or auditd, not by hand; the principle is the same: watch the kernel's facts, not the display's.

3

Prevent: decide what may run

Hiding is free, so prevention targets execution instead. Executable allowlisting means an unknown script dropped into a hidden directory never runs, whatever its name. The tracer gate itself is not preventable by policy: any process may read its own status. What policy can do is narrower: nothing here persists unless something runs it, so the inventory that matters is the process table, taken regularly, not the directory listing.

Honest limit. Every control above watches a layer the attacker can go under. A rootkit underneath (T1014) hides from find, /proc, and the process table alike: no observer comparison helps when the kernel's answers are all mediated. TracerPid itself can be masked by a careful tracer, so the gate is a tripwire, not a guarantee. FIM sees the write only if it was already watching that path, and an allowlist is only as good as its list. This file teaches the layer above the rootkit: changing the observer beats trusting any single view, right up until every view is compromised, and knowing where that boundary lies is the job.

Countermeasures verified

Observers are cross-examined instead of trusted, writes are watched at the kernel's layer, execution is decided by policy, and every control's bypass is stated above.

06

Debrief

TAKEAWAY

Stealth is a stack: every layer defeats one observer and exposes a new surface, so the defender wins by changing observers, not by looking harder through the same one.

IOC checklist: signs this technique was used

  • A process that exits the moment a tracer attaches: tracer-aware behavior is itself the indicator
  • A process whose argv[0] disagrees with its /proc/PID/exe
  • A process executing from a dot-directory under /tmp, /var/tmp, or a service directory
  • Dot-directories appearing outside the usual home-directory clutter

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, bash 5.2, strace, x86-64, on 2026-09-17
  • Both recordings are real executions on that platform, not simulations
  • No privilege needed; no network activity; no persistence mechanisms
  • Cleanup: pkill -f '[s]yslog-helper'; rm -rf /tmp/gh010 (both already run in the blue pass)
