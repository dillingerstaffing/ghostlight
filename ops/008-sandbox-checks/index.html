The Interrogation

Before it does anything, the payload asks where it is. A sandbox looks different from a real machine, and the question costs four reads of public system facts. This file runs the interrogation, then tries to lie to it.

01

Intel Brief

CONTEXT

MITRE ATT&CK T1497.001: before running its payload, malware checks whether it is inside a virtualized or sandbox analysis environment, and stays quiet if it is. This file runs that check end to end, then takes the defender's side of the same question.

Why this technique. A payload that detonates inside an analyst's sandbox burns the sample: the analysts capture the binary, its command-and-control addresses, and the fingerprints of the whole campaign's tooling. So the payload asks one question before it acts: am I being watched. The cheapest form of the question is reading facts the machine volunteers about itself. Four reads, no privilege, nothing written anywhere, and the answer decides whether the payload runs at all.

Why not just one check. The obvious attempt is a single indicator: read product_name, or test one rule like "hypervisor flag means sandbox". Break it on a concrete input: this very lab machine answers systemd-nspawn to systemd-detect-virt and cloud-hypervisor to the firmware reads. One check names only half the machine: a container running inside a VM. And a single string is a single lie to tell: whoever built the sandbox chooses what product_name says. So the working check layers independent channels, the firmware's strings, the CPU's own report, and the init system's detector, and the verdict is an OR across all of them. That layering is also what makes the defense hard: a convincing lie has to falsify every channel, not one.

The mechanism, with terms earned. DMI is the firmware's self-description: the machine's firmware ships tables naming the vendor and the product, and the Linux kernel exposes them as plain text files under /sys/class/dmi/id. sys_vendor names who made the machine; product_name names which machine. The hypervisor flag in /proc/cpuinfo is the CPU reporting, through the kernel, that a hypervisor is present beneath this OS. systemd-detect-virt is systemd's own answer to the same question, built from several of these channels plus container clues. An indicator is one such fact that suggests virtualization. The verdict is the script's final print: indicators present, or none found.

The concrete case, before the abstraction. ./sandbox-check.sh on this lab prints: sys_vendor: Cloud Hypervisor; product_name: cloud-hypervisor; cpu flag: hypervisor; detect-virt: systemd-nspawn; verdict: VM/sandbox indicators present. Four channels, four answers, and they do not even agree with each other: the firmware names a VM, the init system names a container. The machine is both, a container inside a VM, and the layered check is the only reason the verdict sees the whole thing.

Scope. T1497 Virtualization/Sandbox Evasion covers three sub-techniques: .001 System Checks (this file), .002 User Activity Based Checks, .003 Time Based Evasion. This file works the system-checks case end to end: the standard indicators, the verdict logic, and what a defender can and cannot do about a program reading its own environment.

02

Target Environment

LOADOUT

Ubuntu 24.04.5 LTS with bash 5.2, x86-64, itself running virtualized, which is the point: the lab machine is the specimen. The check needs no privilege: every read is a public system fact. The lab stands in for the payload with one script.

1

Build the lab

One directory, one script. The script is the whole payload: it asks where it is, then prints its verdict.

bash
$ mkdir -p /tmp/gh008
$ cat > /tmp/gh008/sandbox-check.sh <<'EOF'
> #!/bin/sh
> # GH-008 lab: the interrogation. A payload's pre-execution check.
> # Reads only public system facts. Nothing is planted, nothing hidden,
> # nothing persists, no privilege needed.
> vendor=$(cat /sys/class/dmi/id/sys_vendor)
> product=$(cat /sys/class/dmi/id/product_name)
> cpuflag=$(grep -m1 -o 'hypervisor' /proc/cpuinfo || echo absent)
> virt=$(systemd-detect-virt)
> echo "sys_vendor:    $vendor"
> echo "product_name:  $product"
> echo "cpu flag:      $cpuflag"
> echo "detect-virt:   $virt"
> blob="$vendor $product $virt $cpuflag"
> case $blob in
>   *[Qq][Ee][Mm][Uu]*|*[Kk][Vv][Mm]*|*VMware*|*VirtualBox*|*Xen*|*[Hh]ypervisor*|*nspawn*)
>     echo "verdict: VM/sandbox indicators present" ;;
>   *)
>     if [ "$virt" != "none" ]; then
>       echo "verdict: VM/sandbox indicators present"
>     else
>       echo "verdict: no VM indicators found"
>     fi ;;
> esac
> EOF
$ chmod +x /tmp/gh008/sandbox-check.sh
2

The payload: the interrogation script

Twenty lines. Every line glossed, because the whole technique lives in this file.

sh: /tmp/gh008/sandbox-check.sh
#!/bin/sh
# GH-008 lab: the interrogation. A payload's pre-execution check.
# Reads only public system facts. Nothing is planted, nothing hidden,
# nothing persists, no privilege needed.
vendor=$(cat /sys/class/dmi/id/sys_vendor)
product=$(cat /sys/class/dmi/id/product_name)
cpuflag=$(grep -m1 -o 'hypervisor' /proc/cpuinfo || echo absent)
virt=$(systemd-detect-virt)
echo "sys_vendor:    $vendor"
echo "product_name:  $product"
echo "cpu flag:      $cpuflag"
echo "detect-virt:   $virt"
blob="$vendor $product $virt $cpuflag"
case $blob in
  *[Qq][Ee][Mm][Uu]*|*[Kk][Vv][Mm]*|*VMware*|*VirtualBox*|*Xen*|*[Hh]ypervisor*|*nspawn*)
    echo "verdict: VM/sandbox indicators present" ;;
  *)
    if [ "$virt" != "none" ]; then
      echo "verdict: VM/sandbox indicators present"
    else
      echo "verdict: no VM indicators found"
    fi ;;
esac

Line by line. #!/bin/sh runs the file under the system shell. The comment lines say what the file is for; they do nothing. vendor=$(cat /sys/class/dmi/id/sys_vendor) reads the firmware's vendor string; $(...) captures a command's output into a variable. product=... reads the firmware's product string. cpuflag=$(grep -m1 -o 'hypervisor' /proc/cpuinfo || echo absent) searches the kernel's CPU report for the hypervisor flag: -m1 stops at the first match, -o prints only the matched word, and the || echo absent runs only if grep finds nothing, so the variable always has a value. virt=$(systemd-detect-virt) asks systemd for its one-word virtualization verdict. The four echo lines print the four indicators: this is the interrogation, the asking, done in public. blob="$vendor $product $virt $cpuflag" concatenates every indicator into one string so a single match tests all channels at once. case $blob in is shell pattern matching against that string: the long pattern lists fragments of known VM vendor and product names (QEMU, KVM, VMware, VirtualBox, Xen, Hypervisor, nspawn), with [Qq] matching either case; if any fragment appears anywhere in the blob, the verdict is indicators present. The *) fallback covers the case where no fragment matched: it still checks $virt, and anything systemd reported other than "none" counts as an indicator. The final else prints "no VM indicators found". Note what that line does not say: it does not say bare metal. It says the four channels were quiet.

03

Phase Red: ask where it is

ATTACK

Four reads, one verdict. Run each indicator by hand first, so you see what the script sees, then run the script and watch it decide. Every command below is copy-pasteable.

1

Read the firmware strings

The kernel exposes the firmware's self-description as text files. Two reads, no privilege.

bash
$ cat /sys/class/dmi/id/sys_vendor /sys/class/dmi/id/product_name
Cloud Hypervisor
cloud-hypervisor

The firmware says this machine is a Cloud Hypervisor guest. Remember who writes these strings: the hypervisor. A hypervisor that wants to lie sets them to anything it likes; the read itself cannot tell a true string from a false one.

2

Ask the CPU and the init system

Two more channels, independent of the firmware strings.

bash
$ grep -m1 -o hypervisor /proc/cpuinfo; systemd-detect-virt
hypervisor
systemd-nspawn

The hypervisor flag means the CPU told the kernel a hypervisor sits underneath this OS. systemd-detect-virt says systemd-nspawn: this shell runs inside a container. Note the disagreement with step 1: the firmware names a VM, the init system names a container. Both are true. One check would have told half the story; that is the concrete failure the layered check fixes.

3

Run the interrogation

The same four facts, now as one verdict.

bash
$ ./sandbox-check.sh
sys_vendor:    Cloud Hypervisor
product_name:  cloud-hypervisor
cpu flag:      hypervisor
detect-virt:   systemd-nspawn
verdict: VM/sandbox indicators present

A payload that wanted a sandbox would stop here: stay quiet, phone nothing home, leave no behavior to analyze. The interrogation cost four reads and printed its decision to the terminal.

Stealth confirmed

The payload learned exactly where it is from public system facts before doing anything else. Nothing was planted, nothing persisted, no privilege was used, and no defender had any separate fact to check: the reads the attacker makes are the same reads the machine offers everyone.

04

Phase Blue: the same facts, the other side

DEFENSE

The red phase asked the machine where it is. Now ask the defender's questions: what does the defender see that the attacker does not, what does the checking look like from outside, and what happens when the machine lies. Every command below is copy-pasteable.

Here is the trap: treating the indicator strings as hostile artifacts and hunting for them. The strings are not hostile. Your own inventory tooling reads the same files. The check is not an object to find; it is a behavior to observe, and a question you cannot stop from being asked.

1

The defender's inventory: the same public facts

The defender runs the same four reads. Watch the answers match the attacker's exactly.

bash
$ cat /sys/class/dmi/id/sys_vendor; cat /sys/class/dmi/id/product_name; grep -m1 -o hypervisor /proc/cpuinfo; systemd-detect-virt
Cloud Hypervisor
cloud-hypervisor
hypervisor
systemd-nspawn

Identical answers. That is the first defensive fact, and it is a negative one: there is no defender-only channel here. The defender reads the same files the payload reads. You cannot stop a program from reading its own environment; the files are world-readable by design. Defense has two moves, and only two: lie to the check convincingly (step 3), or watch the checking happen (step 2).

2

Watch the checking, not the facts

The reads are legitimate, but their pattern is distinctive: one process, at startup, opening the DMI files and cpuinfo in a burst. strace -f follows the script and its children; -e trace=openat shows only file opens; the script's own output is discarded and the log is mined for the interesting paths.

bash
$ strace -f -e trace=openat -o trace.log ./sandbox-check.sh >/dev/null 2>&1
$ grep -oE '/sys/class/dmi/id/[a-z_]+|/proc/cpuinfo' trace.log | sort -u
/proc/cpuinfo
/sys/class/dmi/id/product_name
/sys/class/dmi/id/sys_vendor

That burst is the interrogation's observable footprint. A monitor shaped like this, DMI and cpuinfo reads clustered at process start, sees the checking even when it cannot judge the verdict. This rule is the site's own construction: D3FEND 1.6.0 maps no defender to T1497.001 specifically (its T1497 defenders target time-based evasion), so the Sources section says so plainly instead of borrowing a link that does not fit.

3

The lying room: falsify one channel, watch the verdict hold

Defense move one is deception: a sandbox that lies convincingly. This step builds a small lying room with unshare: a mount namespace where /sys/class/dmi/id is a tmpfs holding forged strings, Dell Inc. and PowerEdge R750, a bare-metal costume. The namespace is contained; nothing on the host changes, and the room vanishes when the command exits.

bash
$ unshare -rm sh -c 'mount -t tmpfs tmpfs /sys/class/dmi/id && printf "Dell Inc." > /sys/class/dmi/id/sys_vendor && printf "PowerEdge R750" > /sys/class/dmi/id/product_name && ./sandbox-check.sh'
sys_vendor:    Dell Inc.
product_name:  PowerEdge R750
cpu flag:      hypervisor
detect-virt:   systemd-nspawn
verdict: VM/sandbox indicators present

The firmware strings lied, and the verdict did not move. The remaining channels, the CPU flag and systemd's detector, still told the truth, and the OR logic only needs one honest channel. This is the bar deception must clear: a convincing sandbox falsifies every channel the check reads, not one. Miss a single channel, and the interrogation still convicts you.

Detection verified

The interrogation is observable as a burst of DMI and cpuinfo reads at process start, even though no single read is hostile. And the lying-room run proved the checker's trust boundary: it believes whatever the environment tells it, so the defense is to control the environment completely or not rely on the verdict at all.

05

Countermeasures

DEFENSE

Three moves, in order: do not let the verdict decide, watch the checking, make the lie airtight. Each is one way, not the way.

1

Mitigate: never let the payload's verdict decide

The check only protects the payload if you honor its decision to stay quiet. Detonate anyway: run the sample in a disposable, instrumented VM regardless of what its interrogation concludes, and capture everything it does. Static analysis sidesteps the question entirely: the checker's strings and branches are visible without executing anything. Either way the interrogation becomes theater: it asked, and nobody listened.

2

Monitor: watch for the read burst

The strace pattern from Phase Blue is the monitor: a cluster of opens on /sys/class/dmi/id/* and /proc/cpuinfo at process start, before the process does anything else. Production versions run it in the EDR or auditd, not strace, and alert on the pattern, not on any single read. This is the fleet form of the check: the idea does not change, only the coverage.

bash
$ strace -f -e trace=openat -o trace.log ./sandbox-check.sh >/dev/null 2>&1
$ grep -oE '/sys/class/dmi/id/[a-z_]+|/proc/cpuinfo' trace.log | sort -u
/proc/cpuinfo
/sys/class/dmi/id/product_name
/sys/class/dmi/id/sys_vendor
3

Prevent: build the lie the checker cannot see through

Falsify every channel the interrogation reads, and keep them consistent: DMI strings via the hypervisor's firmware-string controls, the hypervisor CPUID bit hidden by the hypervisor itself, and the container layer camouflaged so systemd-detect-virt answers none. Or skip the arms race: detonate on bare metal reimaged from known-good media, where there is nothing to detect. D3FEND maps no defender to this sub-technique; the controls above are the site's own, and their limits are stated below.

Honest limit. Every one of these checks is trivially fooled by a sandbox that bothers to lie; absence of VM indicators proves nothing about bare metal, it proves the four channels were quiet. DMI strings are written by whoever built the VM. The hypervisor flag can be hidden by the hypervisor. The read-burst monitor misses checks that execute the CPUID instruction directly instead of reading files, and it races any check that runs before the monitor attaches. Static analysis misses packed or obfuscated checks. And the deepest limit: the checker's verdict is only useful to the attacker if the analyst lets the sample decide whether to run. Run it anyway, in a room you control, and the interrogation answers to an empty room.

Countermeasures verified

The interrogation cannot be prevented, only answered dishonestly or observed in the act. A sandbox that falsifies every channel defeats the check; a monitor that watches the read burst sees it coming; an analyst who detonates anyway makes the verdict irrelevant. None of them changes the core fact: a program can always read its own environment.

06

Debrief

TAKEAWAY

A program can always read its own environment; the defense is to lie to it completely or watch what it does with the answer.

IOC checklist: signs this technique was used

  • A process opening /sys/class/dmi/id/* and /proc/cpuinfo in a burst at startup, before any other behavior
  • DMI vendor or product strings naming a hypervisor (Cloud Hypervisor, QEMU, VMware, VirtualBox) on a machine inventoried as physical
  • systemd-detect-virt disagreeing with the DMI strings: a container inside a VM, or the reverse
  • Execution that stops or goes quiet immediately after the DMI and cpuinfo reads: the verdict told it not to run
  • Known VM-vendor substrings in a binary's readable strings (qemu, kvm, vmware, virtualbox, xen, hyper-v)

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, bash 5.2, x86-64, on 2026-09-17 (the host itself virtualized: a Cloud Hypervisor VM running a systemd-nspawn container)
  • Both recordings are real executions on that platform, not simulations
  • The check runs fully unprivileged: every read is a world-readable system fact
  • The lying-room demo needs unprivileged user namespaces (unshare -rm); it is contained to its own mount namespace and nothing persists
  • Cleanup: rm -rf /tmp/gh008
