The False Name

A process named cron is running on this machine. It has never done a cron job in its life. One command put it there; one command proves it is lying. This file runs both.

01

Intel Brief

CONTEXT

MITRE ATT&CK T1036: adversaries name their tools after trusted system processes, so a human scanning the process list reads straight past them. This file forges the name, then checks the one thing the name cannot change.

Why this technique. The process list is the first thing every triage reads: ps, top, htop, every SIEM process feed. Operators scan names, not hashes; nobody hashes ten thousand processes on a glance. The name is the index the defender reads, and it is the cheapest thing on the system to forge. Renaming the binary renames the process for free, and nothing in the kernel objects.

Why not just check every hash. At fleet scale you can, and D3FEND's file-hashing defenders exist for exactly that. But the human in the loop still triages by name first, and the human is who this technique targets. The name said cron, and for most operators that would have been enough.

Why the name is not the process. In the demo's ps -C cron -o pid,comm,args, the two columns both headed COMMAND are different things: the first is comm, the kernel's 16-byte name derived from the executable's basename at exec time; the second is args, the command line, which begins with argv[0], the invocation name, data the process supplies about itself. Both are labels. The executable itself is the file the kernel mapped and ran, and the kernel remembers which one: /proc/<pid>/exe is a symlink the kernel maintains to that file. Rename the file and the labels follow; the symlink still points at the truth.

The concrete case, before the abstraction. cp sleeper cron && ./cron & puts a process on the box. ps -C cron -o pid,comm,args prints a row that says cron. readlink /proc/<pid>/exe prints /tmp/gh004/cron. Same process, two answers. Only the second one is the kernel's.

Terms, earned. argv[0] is the name a program was invoked with; ps shows it as COMMAND, and whoever launches the process chooses it. comm is the kernel's 16-byte process name, set from the executable's basename when it starts (a process can also rewrite it with prctl, which is why the blue phase does not trust comm either). /proc/<pid>/exe is the symlink the kernel keeps to the file that was actually executed. Masquerading is T1036: presenting hostile code under a trusted name.

Scope. T1036 covers renamed files, spoofed paths, mismatched icons, and more. This file works the process-name case end to end: the label every operator reads first, and the one check that sees through it.

02

Target Environment

LOADOUT

Ubuntu 24.04.5 LTS with gcc 13, x86-64, in a disposable VM used only for this lab. The attack needs no privilege at all: any user can name a file cron and run it. Run it on a throwaway box anyway, because you are about to practice lying to your own tools.

1

Build the lab

One C file for the payload: sleeper.c. It does nothing but sleep, because the payload's behavior is irrelevant; only its name matters.

bash
$ gcc -O2 -o sleeper sleeper.c
2

The payload: sleeper.c

Twelve lines. It sleeps forever, so it stays on the process list long enough to be inspected. Everything interesting about this file happens to its filename, not its code.

c: sleeper.c
/* sleeper.c - GH-004 lab payload: sleeps forever.
 * Its behavior is irrelevant; only its name matters.
 * The red phase copies it to ./cron and runs it. */
#include <unistd.h>

int main(void) {
    for (;;) pause();
    return 0;
}
03

Phase Red: wear the uniform

ATTACK

Three commands. Copy the payload, rename it to cron, run it. Then ask the process list who is running, and believe the answer the way a tired operator would.

1

Copy, rename, run

The whole attack is a filename. No exploit, no privilege, no code change: the binary is byte-identical to the harmless sleeper.

bash
$ cp sleeper cron
$ setsid ./cron &
$ ps -C cron -o pid,comm,args
    PID COMMAND         COMMAND
  16946 cron            ./cron

There it is: a cron process, pid 16946. ps -C matched on comm, which the kernel set from the basename cron at exec time. Nothing about this row is false except the implication. An operator skimming for anomalies sees a daemon name they expect and moves on; that moving on is the entire technique.

Stealth confirmed

An unprivileged user put a process named cron on the box with three commands, and the standard process listing vouches for the name. The forgery cost nothing and the listing detected nothing, because the listing was never checking.

04

Phase Blue: ask the kernel

DEFENSE

ps asked the process for its name and printed the answer. Now ask the kernel a question the process cannot answer for itself: which file did you actually execute.

Here is the trap: opening htop, seeing cron, and closing htop. The name is data the process supplied, laundered through a trusted tool. The check that works does not read any label. It reads the kernel's own record of the execution.

1

Find the suspect, read the kernel's record

Same pid ps just vouched for. Two different questions, two different answers.

bash
$ CPID=$(pgrep -x cron); echo "suspect pid: $CPID"
suspect pid: 16946
$ readlink /proc/$CPID/exe
/tmp/gh004/cron

The name said cron. The kernel says the executed file is /tmp/gh004/cron: a user-compiled binary sitting in a world-writable temp directory. The real cron lives in /usr/sbin and is started by PID 1, not by a shell in /tmp. The process did not lie about anything it controls; it simply never controlled the exe link. That is the whole detection: compare what the process claims with what the kernel recorded, and believe the kernel.

Detection verified

One readlink exposed the forgery ps could not see. The check costs nothing, needs no baseline, and works on any Linux: the name is the process's claim, the exe link is the kernel's record.

05

Countermeasures

DEFENSE

Three moves, in order: remove it, sweep for its siblings, make the trick harder to run. Each is one way, not the way.

1

Mitigate: kill the impostor

It is an ordinary unprivileged process. Killing it ends the masquerade; there is no persistence here, no rootkit, no reinfection. Confirm the exe path first, so you kill the impostor and not the real daemon.

bash
$ readlink /proc/$(pgrep -x cron)/exe
/tmp/gh004/cron
$ pkill -x cron
2

Monitor: sweep for executables in writable dirt

The tell was not the name; it was the address. System daemons do not execute from /tmp, /dev/shm, or /var/tmp. One line lists every process whose executable lives in a world-writable directory.

bash
$ ls -l /proc/[0-9]*/exe 2>/dev/null | grep -E '/(tmp|dev/shm|var/tmp)'
lrwxrwxrwx 1 root root 0 Sep 16 15:27 /proc/17306/exe -> /tmp/gh004/cron

Run it on a timer across the fleet and you have the whole monitor; production versions add alerting, not new ideas. D3FEND names the heavier forms File Hashing (D3-FH) and File Integrity Monitoring (D3-FIM): hash what runs, and notice when a trusted name points at an untrusted file.

3

Prevent: take away the stage

The forgery needs two things: a writable directory and permission to execute from it. Mount /tmp, /dev/shm, and /var/tmp with noexec and the copy-rename-run sequence dies at the exec step. AppArmor or SELinux profiles do the same job per-application.

Honest limit. noexec breaks legitimate installers that stage in /tmp, and a determined attacker writes elsewhere: $HOME, /var/tmp on a lazy admin's box, a mounted USB. This control raises the cost of the trick; it does not remove the trick. The exe check in Phase Blue works regardless of where the file sits, which is why detection outlives prevention here.

Countermeasures verified

The impostor is an ordinary process, so killing it is trivial. The writable-directory sweep finds its siblings fleet-wide with one line. noexec and mandatory access control narrow where the trick can run. None of them changes the core fact: names are claims, and claims get checked against the kernel.

06

Debrief

TAKEAWAY

ps asks the process for its name. /proc/PID/exe asks the kernel where the file lives. When they disagree, believe the kernel.

IOC checklist: signs this technique was used

  • A process whose name matches a system daemon while /proc/<pid>/exe points at a user-writable path
  • Executables running from /tmp, /dev/shm, or /var/tmp
  • Duplicate daemon names: two crons, two sshs, where the inventory says one
  • Daemon-named processes whose parent is a user shell instead of PID 1
  • argv[0] / comm mismatches across the fleet: the name the process reports vs the file the kernel ran

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, gcc 13, x86-64, on 2026-09-16
  • Both recordings are real executions on that platform, not simulations
  • The attack runs fully unprivileged: any user can name a file cron and execute it
  • Cleanup: pkill -x cron; rm -f /tmp/gh004/cron /tmp/gh004/sleeper
