01

Intel Brief

CONTEXT

MITRE ATT&CK T1205.001: adversaries use port knocking, a connect sequence that signals a hidden service to open, so the service port stays closed to everyone else. The actors, named once: the attacker planted the knock daemon on this box during the initial breach and knows the sequence; the defender owns the box, does not know the daemon is there, and runs the scans. This file runs the knock wrong, runs it right, and shows the one inventory that sees through it.

Why this technique. An open port is an advertisement. Every scan on the network sees it, fingerprints the banner, and hammers the login. The port is the problem before the password is: the defender's scan finds the door, and after that the only question is how long the lock holds. Port knocking deletes the advertisement. The service port stays closed, so the defender's scan finds nothing to attack. There is no door to fingerprint until the daemon hears the right sequence, and the sequence is just three connects to three ports that each accept and instantly close.

Why not leave the port open and protect it with a password. That is the obvious defense, and this file breaks it on the concrete input: the defender's scanner sees an open 4000 before any password is ever typed. The banner gives away the service, the open port gives away the address, and the password only changes what happens after the knock on the door is already heard. A password protects the login; it does not hide the door.

Why not scan for the door. The defender's scanner sweeps 3999 to 4004 and finds three ports that accept and close with nothing behind them, and no 4000 at all. It did not miss the door; the door was never there. Scanning answers the question "what is open"; port knocking makes the answer "nothing worth attacking".

The mechanism, in one line. Port knocking is traffic signaling with connects: a knock sequence is an ordered list of connection attempts to specific ports inside a time window. A listener is a process holding a port open. The daemon watches its knock ports, and when the last three knocks match the sequence inside ten seconds, it binds the door port. The baseline is the known-good list of listeners; the allowlist is the set of ports permitted inbound. Terms earned, no borrowing.

The concrete case, before the abstraction. The attacker's daemon holds 4001, 4002, 4003. Knock 4003, 4002, 4001 and nothing happens. Knock 4001, 4002, 4003 inside ten seconds and port 4000 answers with one banner. One python process, four ports, ten seconds.

Scope. T1205 covers traffic signaling broadly: port knocking, and the port-sequence variant where the signal is a specific order of connects. This file works the connect-sequence case end to end: the knock, the door, and the listener inventory that catches it.

The daemon: 51 lines

Line by line. #!/usr/bin/env python3 runs the file under python3. The three imports: socket for the listeners, threading so the three knock ports listen at once, time for the knock window. HOST = '127.0.0.1' keeps the lab local, nothing leaves the box. DOOR = 4000 is the service port, dark until the right knock. KNOCK_PORTS = [4001, 4002, 4003] is the knock sequence, in order. WINDOW = 10.0 means the full sequence must land inside ten seconds. BANNER is the one line the door serves. state holds the knock log and the door flag; lock guards them because three listener threads write the log at once.

serve_door() is the service: it builds a socket, sets SO_REUSEADDR so a restart rebinds cleanly, binds (HOST, DOOR), listens, then loops forever: accept a connect, sendall(BANNER), close. Every connect gets the banner, and once this function starts the door stays up. listen_on(port) holds one knock port the same way, and its loop is the whole technique: accept each connect and close it immediately, so the knock leaves no service to attack, then under the lock append (port, time.monotonic()) to the knock log. last3 is the last three knocks. The if checks four things: three knocks exist, the door is not already up, the three ports are [4001, 4002, 4003] in order, and the third knock landed within ten seconds of the first. All four true, and the daemon spawns serve_door in a background thread. The bottom three lines start one listen_on thread per knock port, then threading.Event().wait() sleeps forever; killing the process stops the daemon.

python: daemon
$ cat > /tmp/gh013/knockd.py <<'EOF'
#!/usr/bin/env python3
"""GH-013 lab: the knock daemon. A door that opens only for the right knock."""
import socket
import threading
import time

HOST = '127.0.0.1'               # lab-local; nothing leaves this box
DOOR = 4000                      # the service port, dark until the right knock
KNOCK_PORTS = [4001, 4002, 4003]  # the knock sequence, in order
WINDOW = 10.0                    # the full sequence must land inside 10 seconds
BANNER = b'GH-013 door open\r\n'

state = {'knocks': [], 'door_up': False}
lock = threading.Lock()


def serve_door():
    """Serve the door: every connect gets the banner, then the door stays up."""
    srv = socket.socket()
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind((HOST, DOOR))
    srv.listen(5)
    while True:
        conn, _ = srv.accept()
        conn.sendall(BANNER)
        conn.close()


def listen_on(port):
    """Hold one knock port: accept each connect, close it, log the knock."""
    srv = socket.socket()
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind((HOST, port))
    srv.listen(5)
    while True:
        conn, _ = srv.accept()
        conn.close()
        with lock:
            state['knocks'].append((port, time.monotonic()))
            last3 = state['knocks'][-3:]
            if (len(last3) == 3 and not state['door_up']
                    and [p for p, _ in last3] == KNOCK_PORTS
                    and last3[-1][1] - last3[0][1] <= WINDOW):
                state['door_up'] = True
                threading.Thread(target=serve_door, daemon=True).start()


for port in KNOCK_PORTS:
    threading.Thread(target=listen_on, args=(port,), daemon=True).start()

threading.Event().wait()  # sleep forever; kill stops the daemon
EOF

Phase Red: knock, and the door appears

ATTACK

First, the defender's scanner's view before any knock: you are the attacker, you know the sequence, so you never scan; this is the view your technique defeats. Then the wrong knock, which the daemon ignores. Then the right knock, which builds the door. Watch what the defender's scan sees, and what it never sees.

1

The defender's scanner, before the knock

You are the attacker. You know the knock sequence, so you never scan this box; the scan below is the defender's, the view this technique defeats. The sweep covers 3999 to 4004, before any knock, and it hits the ports out of order on purpose: sweeping 4001, 4002, 4003 in order would itself be the knock. 4001, 4002, and 4003 accept and close instantly: nothing to attack. 4000, the service port, is closed. The door is open

The banner answered. The attacker's work is done: the door exists, the knock is known, and the service is reachable to anyone who knocks. What the defender sees in this box, the scan that misses and the inventory that catches, is the next phase's business.

Stealth confirmed

The defender's scan found nothing to attack: three ports that accept and close, no service port. The wrong sequence earned silence. The right sequence built the door out of nothing. A defender's scanner that never knocks will never find 4000, because until the knock it does not exist.

Phase Blue: inventory the listeners

DEFENSE

The defender does not scan for the service; the defender inventories the listeners. One ss, one pid, one binary, one window, then the kill.

Here is the trap: sweeping the ports again after the knock and calling the open 4000 the finding. The open door is the one thing the technique shows only to someone who already knows the knock. The detection is the listener inventory: one python process squatting on a run of adjacent ports that serve nothing.

Stop and drop

iptables-save first: never touch the firewall without a way back. The DROP goes in while the daemon is still alive, so the control is proven, not assumed: iptables -A INPUT -p tcp --dport 4000:4003 -j DROP, and the next knock to 4001 dies in the firewall while the packet counter on the rule climbs. (iptables prints a warning about the tcp extension revision; the blocked knock and the counter prove the rule is working.) Then kill $KNOCKD stops the daemon by pid, ps confirms it is dead, and ss -tln confirms all four listeners are gone. Stopping the process is not the whole mitigation; the drop is the part that survives a respawn.

Prevention, demonstrated

The durable form is default-deny inbound with an explicit allowlist: nothing reaches the box unless it is named. Honest limit. iptables rules on the box only stop network reachability. 3

Prevent: default-deny with an explicit allowlist

The durable form: INPUT defaults to DROP, and only named ports are permitted. A knock daemon cannot be reached on ports the firewall never allows, and the listener baseline still runs, because prevention and detection are not substitutes. Demonstrated above in targeted form, then removed; the production form is the default-deny policy.

Honest limit. Targeted drops do not stop a daemon that rebinds to an allowed port, so the allowlist must be small and the baseline runs regardless. And none of this stops a local process from binding 127.0.0.1, which is why the allowlist plus the baseline travel together. A firewall filters the network; the inventory watches the box.

Countermeasures verified

The daemon was stopped by pid with its listeners confirmed gone, its ports dropped and the drops removed, the window scoped and persistence swept. The listeners are baselined on a schedule, and the durable posture is default-deny with an allowlist. The knock still works against a box nobody watches; against a watched box it is just noise in the log.

TAKEAWAY

A closed port is not an absent service: inventory the listeners, not the scan.

IOC checklist: signs this technique was used

  • One python process holding several adjacent ports that accept and close with no service behind them
  • Bursts of completed connections (TIME_WAIT) to adjacent ports on a box with no known service there
  • A daemon binary in /tmp whose loop accepts and immediately closes connects
  • A listener that appears only after a burst of connects to neighboring ports
  • Firewall logs showing dropped or completed connects to a tight run of ports
