GH-026 T1548.001 PHASE RED INSIDE

The Borrowed Crown

A binary owned by root sits in the lab with the setuid bit set. On an ordinary machine, anyone who runs it runs as root. On this machine the kernel refuses the transfer, and this file shows you the exact mechanism that refuses it, then hunts the planted bit the way a defender would.

01

Intel Brief

CONTEXT

MITRE ATT&CK T1548.001: adversaries plant setuid and setgid binaries so a later run inherits a privileged identity. This file plants the crown, watches the kernel refuse to transfer it, and names the exact mechanism. Two actors: the attacker, who owns every plant in the red phase; and the defender, who owns every hunt, strip, and rule in the blue phases.

Why this technique. The operating system's core promise is that your processes run as you. setuid is the sanctioned exception: passwd, sudo, and su all need to act with privileges their caller does not have, so the kernel lets a marked binary borrow its owner's identity at exec. An attacker who gains root once plants their own exception: a binary that hands root back on demand, later, without the original hole. The stealth is in the artifact: the plant is a single letter in a directory listing, an s where an x used to be. No new user, no password change, nothing in the account database for an auditor to find.

Why not the obvious alternative. The obvious move for re-entry is a backdoor root account: one new row in /etc/passwd with UID 0. It works, and it is exactly what account inventories are built to catch: the row shows in every user audit, in lastlog, in every compliance scan. The setuid plant shows up in none of those places. The other obvious move is simpler still: just read the secret file. The red phase tries it first, as the unprivileged user, and the kernel answers Permission denied. That denial is the whole reason the crown exists: the file cannot be read as nobody, so the attacker borrows an identity that can.

The mechanism, in one paragraph. The setuid bit is mode 04000. At exec, the kernel sets the process's effective user ID to the file owner's UID; the real UID stays the caller's, and permission checks use the effective one. The setgid bit is mode 02000: the same transfer for the effective group ID and the file's group. In ls -l the owner's x becomes s (-rwsr-xr-x) and the group's x becomes s (-rwxr-sr-x); in octal the modes read 4755 and 2755. One boundary the kernel draws itself: the bits are ignored on scripts. Exec of a #! script runs the interpreter, and the interpreter does not inherit the bit, so the crown has to be a real binary.

The concrete case, before the abstraction. The lab plants /tmp/gh026/crown: root-owned, mode 4755, a reader for a root-only vault holding GHOSTLIGHT-CANARY-026. Run it as the unprivileged user on an ordinary host and the output line reads uid=65534 euid=0, then the canary. Run it in this lab and the line reads uid=65534 euid=65534, then open: Permission denied. Same binary, same bit, different kernel answer. The red phase then runs the control experiment: the crown copied to the root filesystem, where no nosuid flag exists. Still refused. The mount was never the binding constraint.

Terms, earned. The effective UID (euid) is the identity the kernel checks permissions against; the real UID (ruid) is who launched the process. NO_NEW_PRIVS is a per-process kernel flag: once set, exec grants no new privileges, and it can never be cleared. nosuid is a mount flag: the kernel ignores setuid and setgid bits on binaries executed from that mount. T1548.001 is the planting and abuse of these bits for privilege escalation.

Scope. T1548.001 covers planting setuid/setgid binaries and abusing existing ones. This file works the plant end to end: the bit set on disk, the hunt that finds it, the provenance check that convicts it, the evidence-first strip, and the mount hardening that prevents the next one. The canary is a benign token. The lab runs in a disposable PID and mount namespace with a private /tmp; the lab directory is /tmp/gh026; teardown removes it and the namespace's death reaps every stray. Nothing persists outside the lab.

The payload: crown.c

The planted reader, in full. Line by line: the header comment states the contract (benign reader, planted with the bit, refused by this kernel). #include <stdio.h> and <unistd.h> bring file I/O and the UID/GID calls. main takes argc/argv: the vault path comes from argv[1], defaulting to /tmp/gh026/vault, so the setgid twin reuses the same binary on a different vault. buf[128] and FILE *f are the read buffer and handle. The printf line is the instrument of the experiment: it prints ruid, euid, rgid, egid before touching the file, so the transfer, or its refusal, is on the record. fopen(path, "r") is the permission check under test: as the unprivileged user this fails without the crown. Phase Blue: hunt the bit

DEFENSE

The defender never trusts the listing. The defender hunts the bit, convicts by provenance, strips with evidence first, and hardens the mounts. Every command below ran against the planted lab.

Here is the trap: opening the directory listing, seeing two ordinary-looking executables, and moving on. The s is one letter among dozens, and the eye reads -rwsr-xr-x as -rwxr-xr-x at speed. The checks that work never read the listing the way a human does; they ask the kernel for the mode bits directly.

NO_NEW_PRIVS: grep on /proc/1/status shows 1: the control this lab proved live, set on the whole tree, the reason the planted crown never transferred.

05

Countermeasures

DEFENSE

Three moves, in order: strip with evidence first, sweep on a schedule, harden so the next plant cannot transfer. Each is one way, not the way.

1

Mitigate: capture, strip, verify

Proven first against the planted crowns: the hashes, stats, and binaries are captured into evidence/ BEFORE the strip, because the strip changes the artifact. chmod u-s and chmod g-s take the crowns off; the files stay for forensics. ls -l confirms the s is gone; the re-run fails closed. The plant is contained without deleting the evidence it is made of.

2

Monitor: sweep the bits on a schedule

The scheduled form of the phase-blue hunt: find / -perm -4000 -o -perm -2000 on a timer (the lab ran it scoped to /tmp/gh026), diffed against the known-good inventory, alerting only on the diff. The tell is concrete: good is package-owned in a system path; bad is unowned, or owned wrong, or somewhere a crown has no business being. Production versions add the inventory and the alerting, not new ideas. This is D3-FIM as a cron job: watch the setuid inventory, notice when it changes.

3

Prevent: nosuid, inventory, auditd, NO_NEW_PRIVS

Four controls, in increasing strength. nosuid on writable mounts: shown live on this lab's /tmp; on an ordinary host, mount -o remount,nosuid or the fstab entry. Inventory reduction: baseline the legitimate setuid inventory with dpkg -S and chmod u-s what the host does not need (a procedure for the reader's own hosts; this lab touches no host binaries). auditd: the staged rule watches crowned files for writes and attribute changes, loaded where the daemon runs. NO_NEW_PRIVS: proven live in the red phase as the binding control: with it set, no planted crown can ever transfer.

Honest limit. nosuid does not strip existing bits and does not cover other mounts: an attacker who can write to a non-nosuid mount simply plants there, which is why the control ships with the sweep, not instead of it. 06

Debrief

TAKEAWAY

The setuid bit is a request the kernel may refuse: scanners read the request in the mode bits, but only the exec path decides the effective identity. Hunt the bit, convict by provenance, strip with evidence first, harden the mounts.

IOC checklist: signs this technique was used

  • A file with mode 4755 or 2755 outside /usr/bin, /bin, /usr/sbin (the planted crown's shape)
  • A setuid/setgid binary that no package owns (dpkg -S answers "no path found matching pattern")
  • A setuid binary with a recent mtime in a world-writable directory
  • A setuid binary whose owner or group does not match the package default (chown drift on a legitimate path)
  • auditd write/attribute records on a crowned binary, where the watch runs

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, gcc 13.3.0, x86-64, on 2026-10-05
  • Both recordings are real executions on that platform, not simulations
  • The lab runs as root inside a PID and mount namespace (unshare -pfm --mount-proc) with a private /tmp; the lab directory is /tmp/gh026
  • This sandbox runs NO_NEW_PRIVS on the whole process tree (verified on PID 1) and forces nosuid on new mounts: the plant is real, the transfer is refused, both verified live with a control run on the root filesystem
  • Cleanup: rm -rf /tmp/gh026 (recorded); the namespace's death reaps every stray
