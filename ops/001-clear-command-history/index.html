01

Intel Brief

CONTEXT

MITRE ATT&CK T1070.003: adversaries clear command history to hide what they ran. Shell history feels like a record, but it is a convenience feature owned by the user it records, which means anyone holding that user's shell can erase it in three commands.

The scenario. An intruder lands a shell as ghostdemo on an Ubuntu 24.04 box, does their reconnaissance, then wipes the history before leaving. You are the analyst who logs in afterward and finds nothing. This file runs that wipe, proves the trail is gone, then shows you how to prove it happened and how to make the next attempt fail loudly.

Why this technique matters to victims. On many breached boxes, shell history is the only record of what the intruder typed. When it is gone, most analysts stop looking. The four detection methods in Phase Blue assume you set up nothing in advance.

02

Target Environment

LOADOUT

Any full virtual machine running Ubuntu 24.04. Use a dedicated test account, never a production box.

1

Confirm the OS and shell

Every output below is what these commands actually returned on the verification box.

bash
$ cat /etc/os-release | head -2
PRETTY_NAME="Ubuntu 24.04.5 LTS"
NAME="Ubuntu"
$ bash --version | head -1
GNU bash, version 5.2.21(1)-release (x86_64-pc-linux-gnu)
2

Create the test account

bash
$ sudo useradd -m -s /bin/bash ghostdemo

03

Phase Red: the Wipe

ATTACK

Three commands. That is the entire attack. Watch it work, then verify the trail is gone.

1

Seed normal activity

First, give the account a history worth stealing. Log in as ghostdemo and work normally.

bash
$ su - ghostdemo
ghostdemo@lab:~$ echo "analyst morning check: uptime"
ghostdemo@lab:~$ uptime
ghostdemo@lab:~$ echo "analyst morning check: disk usage"
ghostdemo@lab:~$ df -h / | tail -1
ghostdemo@lab:~$ wc -l ~/.bash_history
4 /home/ghostdemo/.bash_history
2

Run the wipe

The intruder does their reconnaissance, then erases it. Press RUN REPLAY: this is the literal verified session.

ATTACK RUN, ghostdemo@lab VERIFIED 2026-09-15
ghostdemo@lab:~$ whoami
ghostdemo
ghostdemo@lab:~$ id
uid=1000(ghostdemo) gid=1000(ghostdemo) groups=1000(ghostdemo)
ghostdemo@lab:~$ ls /home
ghostdemo hatch
ghostdemo@lab:~$ unset HISTFILE
ghostdemo@lab:~$ history -c
ghostdemo@lab:~$ rm -f ~/.bash_history
ghostdemo@lab:~$ echo "checking the damage:"
checking the damage:
ghostdemo@lab:~$ history
1 history
ghostdemo@lab:~$ ls -la ~/.bash_history
ls: cannot access '/home/ghostdemo/.bash_history': No such file or directory
READY
Stealth confirmed

whoami, id, and ls /home ran and left no trace. The history file is gone and the shell remembers nothing. If history were your only record, the intruder was never here.

3

The companion move

Attackers rarely stop at one wipe. A classic companion is planting the wipe in ~/.bash_logout, so every logout clears the session automatically. Plant it now; Phase Blue will find it.

bash
$ echo 'history -c' >> ~/.bash_logout
04

Phase Blue: Detection

DEFENSE

Four independent ways to prove the wipe happened. None of them require anything you set up in advance.

1

The absence is the evidence

A healthy account accumulates history. An account with known activity and an empty history file is already telling you something. Check what the file looks like now, and when it starts.

bash
$ ls -la ~/.bash_history
ls: cannot access '/home/ghostdemo/.bash_history': No such file or directory
$ history | wc -l
1

Subtlety: a fresh shell recreates the file on exit, so a wiped box often shows a history file that starts after the incident window. Compare the oldest entries against when you know the account was active.

2

Correlate sessions with commands

Logins that produced no commands are the tell. These three commands answer: who logged in, when was the last login, and what did sshd see.

bash
$ last ghostdemo | head
$ lastlog -u ghostdemo
Username         Port     From             Latest
ghostdemo                             **Never logged in**
$ journalctl _COMM=sshd --since "2 hours ago" | grep "session opened"

Reading this output. This verification box used local shells, so last legitimately shows nothing for ghostdemo. On any box with SSH logins, these commands show the sessions, and sessions with no corresponding history entries are your evidence of a wipe.

3

Hunt for tampering

One grep across the shell's startup and shutdown files. The stock Ubuntu comments are noise; anything else is a finding.

TAMPER HUNT, analyst@lab VERIFIED 2026-09-15
analyst@lab:~$ grep -rn "HISTFILE\|history -c" ~/.bashrc ~/.profile ~/.bash_logout /etc/profile.d/ 2>/dev/null
/home/ghostdemo/.bashrc:18:# for setting history length see HISTSIZE and HISTFILESIZE in bash(1)
/home/ghostdemo/.bashrc:20:HISTFILESIZE=2000
/home/ghostdemo/.bash_logout:8:history -c
READY
Detected

The .bashrc hits are stock Ubuntu comments. The .bash_logout hit is the planted wipe. One grep, one finding, and you now know the wipe re-arms on every logout.

4

Watch the file die

If you catch it live, or want to prove the mechanism to a skeptic: watch the history file in one terminal while the attack runs in another. The watcher sees the deletion even though the file is gone.

FILE WATCH, analyst@lab VERIFIED 2026-09-15
analyst@lab:~$ inotifywait -m -e delete_self,delete,attrib,move_self --format '%T %e %f' --timefmt '%H:%M:%S' /home/ghostdemo/.bash_history
Setting up watches.
Watches established.
04:42:20 ATTRIB
04:42:20 DELETE_SELF
READY

DELETE_SELF at 04:42:20 is the rm -f ~/.bash_history landing. Install the watcher with sudo apt-get install -y inotify-tools on Ubuntu.

05

Countermeasures

DEFENSE

First stop the bleeding, then make the next attempt fail loudly. Each layer names its bypass.

1

Mitigate: preserve and sweep

Do not reboot yet; memory and logs are evidence. Copy what remains somewhere safe, then sweep for the companions this technique travels with.

bash
$ sudo mkdir -p /root/case-gh001
$ sudo cp -a /home/ghostdemo/.bash_history /root/case-gh001/ 2>/dev/null
$ sudo journalctl --since "24 hours ago" > /root/case-gh001/journal.txt
$ grep -rn "HISTFILE\|history -c" /home/*/.bash_logout /home/*/.bashrc 2>/dev/null

Then sweep every account with the Phase Blue hunt, check cron tables, authorized_keys, and user systemd units, and rotate the compromised account's credentials plus any secrets it could read.

2

Prevent, layer one: tamper-evident shell logging

A root-owned login snippet that ships every command to the system journal the moment it finishes, and locks the history variables read-only. The attacker can still delete the file. They cannot reach back in time.

bash: /etc/profile.d/shell-audit.sh
# GHOSTLIGHT-001 prevention layer 1: tamper-evident shell logging.
# Root-owned. Every interactive login shell ships each command to the
# system journal the moment it finishes, before an attacker can wipe history.
export HISTTIMEFORMAT='%F %T '
export HISTSIZE=100000
export HISTFILESIZE=100000
shopt -s histappend
PROMPT_COMMAND='history -a; logger -t shell-audit -p authpriv.info "$(id -un) [$$] $(history 1 | sed "s/^ *[0-9]* *//")"'
readonly PROMPT_COMMAND
readonly HISTFILE

Install it root-owned and read-only, then re-run the attack and watch it fail to hide. This is the verified session:

PREVENTION PROOF, ghostdemo@lab VERIFIED 2026-09-15
ghostdemo@lab:~$ echo "morning check: services up"
morning check: services up
ghostdemo@lab:~$ whoami
ghostdemo
ghostdemo@lab:~$ echo "intruder: staging data for exfil"
intruder: staging data for exfil
ghostdemo@lab:~$ ls /etc/*.conf | head -3
/etc/adduser.conf /etc/ca-certificates.conf /etc/debconf.conf
ghostdemo@lab:~$ unset HISTFILE
-bash: unset: HISTFILE: cannot unset: readonly variable
ghostdemo@lab:~$ history -c
ghostdemo@lab:~$ rm -f ~/.bash_history
ghostdemo@lab:~$ echo "intruder: trail is clean"
intruder: trail is clean
READY

The wipe still deleted the file. But every keystroke, including the wipe itself, was already in the journal with a timestamp. Check it:

bash
$ sudo journalctl -t shell-audit -o cat --since "5 minutes ago"
ghostdemo [10446]
ghostdemo [10446] 2026-09-15 08:44:01 echo "morning check: services up"
ghostdemo [10446] 2026-09-15 08:44:01 whoami
ghostdemo [10446] 2026-09-15 08:44:01 echo "intruder: staging data for exfil"
ghostdemo [10446] 2026-09-15 08:44:01 ls /etc/*.conf | head -3
ghostdemo [10446] 2026-09-15 08:44:01 unset HISTFILE
ghostdemo [10446]
ghostdemo [10446] 2026-09-15 08:44:01 rm -f ~/.bash_history
ghostdemo [10446] 2026-09-15 08:44:01 echo "intruder: trail is clean"
Prevention verified

The attacker believed the trail was clean. The journal disagrees, timestamp by timestamp, including the rm itself. Timestamps are system time (UTC on the verification box).

Bypass, stated honestly. A shell started with bash --noprofile --norc skips /etc/profile.d entirely, so this layer does not cover an attacker who knows it is there. It raises the cost and catches the careless. The kernel layer below covers everyone.

3

Prevent, layer two: kernel audit watches (full VM only)

Kernel-level file watches cannot be bypassed from user space and survive everything short of root. First, check your environment can run them:

bash
$ sudo auditctl -w /tmp -p wa -k test
The audit system is disabled

If you see The audit system is disabled, you are in a container: run this section in a full VM. We verified this exact failure on a containerized Ubuntu 24.04 box. Where audit runs, the rules are:

bash
$ sudo auditctl -w /home/ghostdemo/.bash_history -p wa -k bash_history
$ sudo auditctl -e 2   # immutable: rules stand until reboot

Re-run the Phase Red wipe, then read the kernel's own account with sudo ausearch -k bash_history -i. The unlink event names the process that deleted the file. Make the rules permanent in /etc/audit/rules.d/ so they survive reboot.

4

Prevent, layer three: ship it off the box

The only record that survives a full compromise of the machine is the one that is not on the machine. Forward the audit stream to a log host:

rsyslog: /etc/rsyslog.d/99-remote.conf
# needs rsyslog installed and a reachable log host
authpriv.* @@loghost.internal:514

On append-only flags. On ext4 and xfs, chattr +a ~/.bash_history makes the history append-only (even root must clear the flag first). On btrfs the flag does not exist: we verified chattr +a fails there with Operation not permitted. Portable answer: the journal and audit layers above.

06

Debrief

TAKEAWAY

Shell history is a convenience, not a control. Treat its absence as evidence, and keep the real record somewhere the shell cannot reach: the journal, the kernel audit log, or another machine.

IOC checklist: signs this technique was used

  • ~/.bash_history missing, truncated, or starting after the incident window
  • history -c or HISTFILE tampering in ~/.bash_logout, ~/.bashrc, ~/.profile, or /etc/profile.d/
  • Logins (last, lastlog, sshd journal) with no corresponding commands
  • File-watch events: DELETE_SELF or unlink on the history file

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, bash 5.2.21, test account ghostdemo, on 2026-09-15
  • Transcripts are the literal commands and outputs; prompts normalized to ghostdemo@lab
  • Journal timestamps are system time (UTC on the verification box)
  • Known environment limits documented inline: containers disable kernel audit; btrfs lacks append-only flags
