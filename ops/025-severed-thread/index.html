01

Intel Brief

CONTEXT

MITRE ATT&CK T1036.009: adversaries sever the parent-child link so the payload's lineage no longer points at its launcher. If the detection leans on the tree, the tree now vouches for nothing. This file cuts the thread, then ties it back together with the two things the cut cannot erase. Two actors: the attacker, who owns the launcher and every write in the red phase; and the defender, who owns every read, hunt, kill, and rule in the blue phases.

Why this technique. The process tree is the first map every triage reads: who launched what, in what order, from where. Endpoint tools that score on the parent-child relationship lean on the same map: a payload whose parent is a user shell reads as user activity, while the same payload under init reads as system furniture. The tree is an index of origins, and origins are what incident response is for. Sever the link and the payload keeps running while its origin stops existing; the map still draws, but the road it used to draw is gone.

Why not just run it and read the tree. The obvious alternative is no tradecraft at all: run the payload directly and let the tree tell the truth. It works: the red phase's baseline starts sleep 600 from the shell, and ps -o pid,ppid,cmd names the launcher in the PPID column while the launcher lives. Break it on the concrete input the technique names: fork twice, let both parents exit before anyone looks. The kernel reparents the surviving grandchild to PID 1, and the same ps query now reports PPID 1 with the launcher unfindable (no such process). The tree was never lying; its input, a live parent, is gone. That is the whole technique: not forging the map, but removing the territory it maps.

The mechanism, in one paragraph. fork() clones the process; the original (the parent) then exits, which orphans the child. Do it twice: the first parent exits, orphaning the child once; the middle child exits, orphaning the grandchild twice. The kernel must put orphans somewhere, so it reparents them to the nearest subreaper, which on a normal system is init, PID 1. The grandchild then calls setsid() to start a new session, detaching from any terminal. What remains is a running process whose PPID is 1 and whose true launcher has exited: the lineage is severed. This is also, unremarkably, how every well-behaved Unix daemon is born; the technique is the abuse of a system feature, not a bug.

The concrete case, before the abstraction. The lab launcher prints its pid (launcher pid: ...) and exits. Its grandchild keeps running: ps -o pid,ppid,cmd reports PPID 1 for it. kill -0 on the launcher pid answers no such process. The forest view draws the payload as a direct child of PID 1. The only record of the launch is the canary file the grandchild wrote itself: GHOSTLIGHT-CANARY-025 launched-pid=.... Same machine, before and after: a child with a parent, then an orphan with a story nobody can check.

Terms, earned. PPID is the parent process ID: the field the tree is drawn from. An orphan is a process whose parent has exited; reparenting is the kernel assigning the orphan to PID 1. A daemon is a background process detached from any terminal, conventionally born by exactly this double fork plus setsid(). init is PID 1, the ancestor every orphan is handed to. The process tree is the PPID linkage drawn as a hierarchy; breaking it is T1036.009.

Scope. T1036 covers masquerading broadly: names, paths, arguments, and lineage. This file works the break-process-trees case end to end: the double fork, the severed lineage, the birth-time hunt, the evidence-first containment, and the staged exec-time watch. The canary is a benign token: it marks the lab payload and nothing else. The lab runs in a disposable PID and mount namespace with a private /tmp; teardown removes the lab directory, and the namespace's death reaps every stray. Nothing persists outside the lab.

Target Environment

LOADOUT

Ubuntu 24.04.5 LTS, x86-64, python3 (3.12.3), root inside a disposable PID and mount namespace used only for this lab. The attack needs no privilege beyond what the launcher already has: any process can fork and exit. The detection needs only read access to /proc.

1

Build the isolated lab

The recording runs inside its own PID and mount namespace with a private /tmp, so every take begins identical. rm -rf /tmp/ghlab starts clean; mkdir -p stages the work directory. longer points at the launcher. Benign: the payload only sleeps, and writes

import sys
import time

CANARY = 'GHOSTLIGHT-CANARY-025'

    main()

The payload: threadcut.py

One file, two roles: the launcher half runs first and exits; the grandchild half is the payload that survives. Line by line: the CANARY and WORK constants name the benign mark and the lab directory. main() prints the launcher pid and writes it to launcher.pid (the pidfile the red phase uses to prove the launcher is gone). The first os.fork(): the parent branch calls sys.exit(0), orphaning the child once. The second os.fork(): the middle branch calls os._exit(0), orphaning the grandchild twice (_exit skips interpreter cleanup, which is the correct way to end a forked child). os.setsid() starts a new session, detaching from any terminal. The grandchild writes the canary launch record (GHOSTLIGHT-CANARY-025 launched-pid=...) and its own pid to payload.pid, then time.sleep(600): the benign hold, ten minutes of doing nothing, so the blue phase has a live orphan to inspect. On a real host the sleep would be the implant; here it is the canary-marked placeholder.

04

Phase Blue: read the birth times

DEFENSE

The defender stops trusting the tree and starts reading what the cut cannot erase: when each process was born, and what the kernel recorded about it at birth.

Here is the trap: opening the forest view, seeing the payload under PID 1, and filing it as system furniture. The tree is not lying; it is answering a narrower question than the one you asked. It says who the parent is now. It says nothing about who the parent was. The checks that work never ask the tree for history; they read the records the cut cannot rewrite.

1

DETECTION: the naive view, and the anomaly in it

The defender starts where the analyst starts: ps -ef --forest draws the payload as a child of PID 1, origin gone. The tree is the claim; now check it against the record. ps -p 1 -o lstart shows when PID 1 was born; ps -p $P -o lstart shows when the payload was born: the fifty-second aging sleep sits between them, so PID 1 is near a minute old and the payload is seconds old. A child of PID 1 born long after PID 1 is the LEAD: init's real children are born at boot, and this one was not. D3FEND names this discipline D3-PLA: Process Lineage Analysis: examining a process's ancestry and the metadata of each node, including execution order and duration relative to its siblings.

$ P=$(cat /tmp/ghlab/payload.pid); echo "suspect pid: $P"
ps -ef --forest
echo '--- the tree says PPID 1; the origin is gone ---'
ps -p 1 -o pid,lstart,etime
ps -p $P -o pid,lstart,etime
echo '--- LEAD: a child of PID 1 born long after PID 1 ---'

DETECTION: the independent observation path

Reparenting rewrites the PPID field; it cannot rewrite the kernel's per-process records. /proc/$P/stat field 4 confirms PPID 1, and field 22 gives the birth time in clock ticks since boot: the payload's ticks sit 5050 ticks after init's, so it was not born of init. readlink /proc/$P/exe names the real interpreter (/usr/bin/python3.12); readlink /proc/$P/cwd names where it was launched from; the canary file carries the launch record the tree deleted. Three independent reads, one finding: the orphan's own files still point at its origin.

The heredoc stages ghostlight-025.rules: an execve watch that records every program execution with its parent at creation time. Reparenting happens after exec, so the audit record keeps the original parentage the tree later loses. command -v auditctl confirms the tooling is installed; pgrep confirms auditd not running in this lab: rule staged, not loaded, stated with its dependency, not demonstrated. Where the daemon runs, the double fork still happens, but the exec record names the launcher that the tree forgot.

# GH-025: record every execve with its parent at creation time (needs auditd running)
-a always,exit -F arch=b64 -S execve -k gh025-exec
-a always,exit -F arch=b32 -S execve -k gh025-exec
EOF

Countermeasures

DEFENSE

Three moves, in order: contain with evidence first, sweep for late-born orphans on a schedule, watch executions at creation time. Each is one way, not the way.

      1 Mon Oct  5 10:23:25 2026       00:51
    PID                  STARTED     ELAPSED
     14 Mon Oct  5 10:24:15 2026       00:01
--- LEAD: a child of PID 1 born long after PID 1 ---

Honest limit. Late-born children of PID 1 are a lead, not a verdict: administrators start services by hand, container entrypoints adopt children, and job schedulers reparent routinely. Every hit needs the exe/cwd cross-check before action, or the sweep pages the on-call for normal operations. And the poll interval sets the floor: an orphan that lives and dies between sweeps leaves no ps trace behind, only the exec-time telemetry, if it was running.

3

Prevent: watch executions at creation time

The staged rule (ghostlight-025.rules) is the durable control: an execve audit watch records every program execution with its parent at creation time, before any fork can orphan it. Reparenting happens after exec, so the record keeps the original parentage the tree later loses. Pair it with executable allowlisting on what may run at all (the D3FEND family names the heavier forms); the watch tells you who launched what, the allowlist narrows what can be launched.

bash
$ mkdir -p /tmp/ghlab/staged
cat > /tmp/ghlab/staged/ghostlight-025.rules <<'EOF'
# GH-025: record every execve with its parent at creation time (needs auditd running)
-a always,exit -F arch=b64 -S execve -k gh025-exec
-a always,exit -F arch=b32 -S execve -k gh025-exec
EOF
cat /tmp/ghlab/staged/ghostlight-025.rules
command -v auditctl
pgrep -a auditd || echo 'auditd not running in this lab: rule staged, not loaded'
# GH-025: record every execve with its parent at creation time (needs auditd running)
-a always,exit -F arch=b64 -S execve -k gh025-exec
-a always,exit -F arch=b32 -S execve -k gh025-exec
/usr/sbin/auditctl
auditd not running in this lab: rule staged, not loaded

Honest limit. The rule needs auditd running with rules loaded; this lab has the binary but no daemon, and many containers lack the subsystem entirely. The watch detects the launch; it does not prevent it. And the deeper limit is the technique itself: MITRE's own mitigation note says this type of attack "cannot be easily mitigated with preventive controls since it is based on the abuse of system features." fork() cannot be forbidden, because daemonization is standard Unix practice: every well-behaved service double-forks. noexec on writable directories does not stop the break either: the break is fork plus exit, not execution from a path. This control makes the severing observable at creation time; it does not remove the severing. That is why detection outlives prevention here.

Countermeasures verified

The orphan's records and hashes were captured before the kill; the kill went by PID and the resweep is clean; the scheduled sweep names its tell, its false-positive load, and its interval floor; the exec-time watch is staged with its dependency stated. Every control names its bypass: /proc dies with the process, late-born orphans include innocent services, and no control forbids fork.

Debrief

TAKEAWAY

The process tree is a claim about parentage that dies with the parent. Birth times and the kernel's per-process records survive it. When the tree says PID 1, check when the child was born.

IOC checklist: signs this technique was used

  • A process with PPID 1 whose start time is long after PID 1's (the late-born orphan; the sweep's LEAD)
  • Launcher artifacts with no launcher: pidfiles, scripts, or canary-style markers in temp directories whose owning process is gone
  • An interpreter running a script from a temp or user-writable directory with PPID 1 and a recent birth time
  • execve audit records (where the watch runs) showing a process whose parent exited within seconds of the exec
  • A cwd or environ pointing at an operator's working directory on a process whose tree position claims init ancestry

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, python3 3.12.3, x86-64, on 2026-10-05
  • Both recordings are real executions on that platform, not simulations
  • The attack runs as root inside a PID and mount namespace (unshare -pfm --mount-proc) with a private /tmp; forking needs no privilege beyond the launcher's own
  • The detection needs only read access to /proc
  • Cleanup: rm -rf /tmp/ghlab; the namespace's death reaps every stray; verify with ps -e --forest
